# LICM as a translation of LLVM's: the plan

TL;DR: `LICM.cpp` (2,897 lines at `d1106deb71cc`) is translated whole, including `promoteLoopAccessesToScalars`, on the translated MemorySSA ([plan](memoryssa-port.md), stage 1 [#2116](https://github.com/ali-mosavian/llrm/pull/2116)); it replaces `hoist.rs` and `loopmotion.rs` and gives the loop-carried global cells back to registers, which real `SROA` and `mem2reg` do not promote and the old leaf `Sroa` plus write-through `Promote` did. Without it three -O3 rows lose (`x_nbody_f`, `fpbench`, `nbody_single`: executed instructions up to 1.19x). Shadow first: decisions only, on the dumped pass inputs, against `opt -passes=licm` counts.

Rule for the code: each Rust function is a translation of the C++ function named in its first comment (permalink), the `cl::opt` defaults stand, and anything not translated is a DEVIATE with a reason and a number.

## 3. What it asks of MemorySSA, and of the alias query

From `LICM.cpp`: `getMemoryAccess(I)` (L1020, L1188), `getBlockAccesses` and `getBlockDefs` (the flags' count), `getDefiningAccess`, `dominates`, the walker's `getClobberingMemoryAccess` with `LicmMssaOptCap`, and the updater: `createMemoryAccessInBB`/`After`/`Before`, `insertDef`/`insertUse` (`RenameUses`), `moveToPlace`, `removeMemoryAccess`. The alias answers are `AA.getModRefInfo` on instruction pairs and `MemoryLocation` pairs through the translated walker's `AliasQuery`: per query, cached, nothing built for the whole function.

`ScalarEvolution` is never an input to a decision in LICM. Its three uses are guarded by `if (SE)` and only drop cached dispositions: `formLCSSARecursively(*L, *DT, LI, SE)` ([`L527`](https://github.com/llvm/llvm-project/blob/d1106deb71cc81016406a1917d0508d2df296266/llvm/lib/Transforms/Scalar/LICM.cpp#L527)), `SE->forgetLoopDispositions()` after a change ([`L543`](https://github.com/llvm/llvm-project/blob/d1106deb71cc81016406a1917d0508d2df296266/llvm/lib/Transforms/Scalar/LICM.cpp#L543)), and `SE->forgetBlockAndLoopDispositions(&I)` when an instruction moves ([`L1244`](https://github.com/llvm/llvm-project/blob/d1106deb71cc81016406a1917d0508d2df296266/llvm/lib/Transforms/Scalar/LICM.cpp#L1244)); the legacy pass gets `SE` from `getAnalysisIfAvailable` ([`L260`](https://github.com/llvm/llvm-project/blob/d1106deb71cc81016406a1917d0508d2df296266/llvm/lib/Transforms/Scalar/LICM.cpp#L260)) and runs with it null when it is not scheduled. llrm has no `ScalarEvolution` to invalidate, so each is a no-op, as in LLVM without it; no hoist, sink or promotion changes.

## 4. Stages and gates

| stage | content | gate |
|---|---|---|
| L1 | decisions only: `hoist_region`, `sink_region` and the promotion candidates, on the dumped pass inputs; later decisions see earlier hoists through a moved-set, nothing is edited | counts of hoisted, sunk and promoted per loop against today's `hoist` and `loopmotion` and against the oracle; every difference classified (another pass, a fact LLVM lacks, a gap) |
| L2 | apply: the edits and the `MemorySSAUpdater` calls | MemorySSA stage 3 and the edit contract; updated graph equals a fresh build after every edit |
| L3a | `promoteLoopAccessesToScalars` alone, in the pipeline, `loopmotion` removed: the SROA prerequisite, which can go first and separately | the three -O3 rows recovered; rows reported as in L3b |
| L3b | `hoistRegion` and `sinkRegion` in the pipeline in LLVM's order, `hoist` removed, no forecast | held until the back end answers the over-hoist: `x_radix` -O1 code x1.047 and `lru` -O3 clocks x1.036 without the forecast, and only constants and `lea` with available operands rematerialise on x86 (`imul`, `shl`, `neg`, `add` do not); no waived rows. Rows: the number of rows worse than base for each of clocks, executed instructions, memory operands and code bytes at each level, then the geomean |

## 5. Oracle

Primary: the same IR into both. llvm-difftest's single-pass replay of `opt -passes='loop-mssa(licm)'` (with `-stats` and `-pass-remarks=licm`) on llrm's own pass-input dumps of the corpus, against the translated pass on that module; the replay carries the no-leak test and the `LLRM_*` environment guard. Per function: instructions hoisted, sunk and promoted, and the resulting module where the two agree.

Second check: clang's IR for the same C sources (`clang -O2 -Xclang -disable-llvm-passes -emit-llvm`, then `opt -passes='function(sroa,early-cse<memssa>,simplifycfg,instcombine),loop-mssa(licm)'`) against llrm's MIR at the same point. The two IRs differ (another front end, other passes before), so this is per loop and classified; it is weaker evidence and only a cross-check.

The evidence for the promotion gap is llvm-order-poc's classification of the unpromoted global cells.

## 6. Targets

LLVM `LICMPass` on `d_faces` -O2: 70 loop runs over 9,489 IR instructions, 1,077 instructions per IR instruction. Today's `hoist` on the dumped inputs: 14,069 per IR instruction with the forecast off; on the largest `d_faces` -O2 body 45 M of 78 M are the facts it asks for (`Accesses` with `Annotated`, `Registers`, `Bounded`). `MachineLICM` (8.5 M) is the back end's stage and not in this plan.
