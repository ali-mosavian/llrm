# ScalarEvolution as a translation of LLVM's: the plan

TL;DR: LoopInfo first, then `ScalarEvolution.cpp` (16,469 lines), the Expander (2,625) and `ScalarEvolutionNormalization`/`Division` (413), at `d1106deb71cc`, translated function for function. The SCEV tree replaces `Scev`/`Monomial`/`Recurrence` and the IV discovery in `induction.rs` and `expand.rs`; `lsr` is the first consumer (89.5 M against LLVM's 10.0 M on `d_faces` -O2, [lsr-vs-llvm](lsr-vs-llvm.md)). Trip counts (`BackedgeTakenInfo`) and the guards that feed them after LVI/CVP belong to indvars-decide-poc and are not translated here.

Rule for the code: each Rust function is a translation of the C++ function named in its first comment (permalink at the pin); `cl::opt` defaults stand; anything not translated is a numbered DEVIATE (section 4) resting on a stated fact about MIR or the target, with an assert or test at the boundary. A stage is not landed until the llrm code it replaces is deleted.

Pinned: LLVM `d1106deb71cc` (clang 24.0.0git), the pinned source and build tree, named in one place by `tools/llvmpin.py` (on `alim/test/clang-pinned`, not yet on main: stage 0 waits on it).

## 1. What exists

**Loops: one structure, three views.** `llrm_mir::forest::Forest` (`forest.rs`, 467 lines) is the one owner of "which blocks are a loop": parent, children, own blocks, depth, innermost loop per block, found in one walk. Three wrappers sit on it:

| view | reads it | becomes |
|---|---|---|
| `graph::loops::{Loop, loops, depth, ...}` in `llrm-analysis` (flat `Vec<Loop>` of `i64` ids, `Body` = forest view) via `cfg::Shape.loops` | the live MIR optimizer: 41 `llrm-transforms` files read `.loops` (lsr, indvars, loopexit, unroll, rotate, lcssa, loopsimplify, hoist, decide, ...); 47 `llrm-transforms` and 18 `llrm-analysis` files import `graph::loops` | `LoopInfo` (stage L1). `graph::loops` keeps the CFG-generic walks that do not know loops (`back_edges`, `irreducible`, `immediate_dominators`, `frontiers`) |
| `llrm_mir::loops::{LoopInfo, Loop}` over `BlockId` (`loops.rs`, 228 lines), the `Loops` analysis `Shape::of` converts into the flat form | `cfg.rs`, `argpromotion`, `interprocedural`, `llrm-mir` binary | deleted: it is `LoopInfo` with a different name and half the API |
| `llrm-codegen::analysis::loops` (`Shaped` per-CFG-shape cache from 479131558, `LirBlock` nodes) | the LIR back end (17 files: `loopslots`, allocation) | stays on `Forest`; its per-shape cache is kept and its test (cache still hits) is the gate for L1 |

`Forest` already has LoopInfo's tree; it lacks LoopInfo's API (header/latch/preheader/exiting/exit blocks, invariance, mutators) and the identity LoopInfo gives a loop (a `Loop` object that survives edits, which SCEV keys `AddRec`s and dispositions on).

**Induction.** `llrm-analysis/src/induction.rs` (3,595 lines): `Scev` + `Monomial` (modular polynomial in invariant unknowns, 2604-2816), `Recurrence` (2816), `basics`/`followers`/`pointers`/`stepping` (IV discovery), `CountedLoop`/`trips`/`exits`/`most_backedges` (trip counts, ~1.5 k), `IvUse`/`Users` (2874-3550). `llrm-mir/src/scalarevolution.rs` (374 lines, `Evolution`) is the rich-MIR copy; it is that session's, and becomes a consumer after S3. `llrm-transforms/src/expand.rs` (266 lines): `Expander`, `sum_of`, `product_of`, `scaled`, `placed`, and #2139's `based()`.

**Consumers.** `lsr.rs` 3,344, `indvars.rs` 1,110, `loopexit.rs` 652; 38 files import `induction::`.

## 2. One owner per fact

| fact | owner | LLVM |
|---|---|---|
| which blocks form a loop, loop tree, loop identity | `LoopInfo` over `Forest` (this plan, L1) | `LoopInfoBase` |
| expression tree, folds, uniquing | `scev::` (S1) | `ScalarEvolution::get*Expr` |
| value range, no-wrap flags of an expression | `scev::` (S2) on `ConstantRange` (valuetracking-port, `llrm_mir::constantrange`, #2143) and `KnownBits` | `getRangeRef`, `setNoWrapFlags` |
| value -> SCEV | `scev::create_scev` (S3) | `createSCEV` |
| loop/block disposition, scope, invalidation | `scev::` (S4) | `getLoopDisposition`, `getSCEVAtScope`, `forget*` |
| implication on SCEVs (`isKnownPredicate`, `isImpliedCond`, `applyLoopGuards`) | `scev::` (S5) | `ScalarEvolution::isImpliedCond*` |
| implication on IR values | valuetracking-port | `ValueTracking::isImpliedCondition` |
| implication in a constraint system | not mine (ConstraintElimination) | `ConstraintSystem` |
| backedge-taken counts, exit limits | indvars-decide-poc | `computeBackedgeTakenCount`, `howFarToZero`, ... |
| instruction costs | cgscc-poc, `tti` module in `llrm-analysis` ([tti-plan](tti-plan.md)) | `X86TTIImpl` |
| expansion | `scev::expander` (S6) | `SCEVExpander` |

The three implication engines stay three: merging them changes what each can prove and their caps (`MaxArithDepth`, `MaxValueCompareDepth`).

## 3. Stages

Each stage is a PR that lands alone, deletes what it replaces, and is gated by section 5.

### L1. LoopInfo (before any SCEV code)

L1b-1 (#2228, draft) makes `analyzeImpl` generic over a `LoopGraph` so LIR and the graph walks use it and `forest::forest` loses its algorithm; L1b-2 (#2231, draft) adds the `Loop` queries memoryssa-port's LICM asked for and `LoopBlocksDFS`/`RPO`. The adapter exits after the lsr/indvars migration in S7 (#2197, owner scev-port).

L1a landed as #2195: `llrm-mir/src/loopinfo.rs`, `analyzeImpl` translated (pinned LLVM finds loops by Wei et al.'s single depth-first search, not by back edges and dominance; the dominator tree is asked only for a re-entered cycle), the `Loop` queries, `tools/loops_oracle.py` (equal to `print<loops>` on 306 corpus files and the irreducible and odd-shape fixtures); `llrm_mir::loops` deleted; `Shape` reads it through `Forest::of_loop_info`. L1b: the mutators below, `analyzeImpl` generic over the CFG so LIR and the graph walks use it and the address forest's builder goes, and the flat `Loop` consumers move.

Module `crates/ir/llrm-mir/src/loopinfo.rs`, over `Forest`. `LoopInfoBase::analyze` becomes `Forest` construction (the walk is the same: dominator tree, back edges, subloop discovery, DFS population).

### S1. Expressions, uniquing, folds

**S1 and S2 land as one stack, on #2143.** `getAddExpr`, `getMulExpr` and the casts call `getRange`, `getMinTrailingZeros` and `StrengthenNoWrapFlags`, and the extension folds of an `AddRec` call `isKnownPredicate`, `isLoopEntryGuardedByCond` and `getBackedgeTakenCount` (S5 and the `BackedgeCounts` seam), so the folds cannot be verified apart from them. The stack is built and verified in pieces against the fold oracle (section 5); it needs `ConstantRange`, `KnownBits` and `computeKnownBits`/`computeConstantRange` from #2143.

The pinned LLVM has `SCEVUse`: an operand carries use-site `nuw`/`nsw` bits (`SCEVUseT`, `SCEVFlags{ExprFlags, UseFlags}`), `SCEV::computeAndSetCanonical` strips them from the operands and `getWithOperands` rebuilds, and uniquing keys on the use bits. They print as `<u nuw>`. Translated as `scev::expr::Use`, with the flags a node gains later (`setNoWrapFlags`) kept on the node.

Module `crates/opt/llrm-analysis/src/scev/` (`expr.rs`, `fold.rs`, `print.rs`). `FoldingSet` becomes an interner (`HashMap<Key, ExprId>` in an arena); `SCEV` is `Copy` ids.

## 5. Oracle and gates

Same IR into both: `llrm-mir` prints a function as LLVM assembly (`print.rs`); the pinned `opt -passes='print<scalar-evolution>' -disable-output` prints, per value, `%v = ... --> {0,+,1}<nuw><%loop> U: [0,10) S: [0,10)` and per loop `Exits:`. `tools/scev_oracle.py` runs the pinned `opt` (version printed, `llvmpin.py` refuses another), parses those lines, and compares them with `llrm-mir --print-scev` (the `scev::print` text) on the same file. Row summaries lead with `rows total / with counters / failed / missing` (`tools/rows/rowcheck.py`, #2145); an error row fails the summary.

**Exit values earn nothing yet.** `rewriteLoopExitValues` is on by default (as LLVM runs it); bench-instruments' rows for #2473 against `LLRM_NO_SCEV_EXITVALUES=1`: no row crosses 1.00, d_faces executes the same on every counter, clocks geomean 0.1% worse, code +0.4..+0.7% (QCport +0.01..+0.06%). What makes it pay is the consumers behind it: `WidenIV` and `LFTR` (a loop's test rewritten against the count it computed), which drop the counters the rewrite leaves unread. It is not extended before one of them shows a row win.

**Fold oracle.** `tools/scev/oracle.cpp` links the pinned `libLLVMAnalysis.a` and builds any expression with LLVM's own `ScalarEvolution` constructors from an s-expression (`(add nuw:- (u 0) (c 16 1))`) over the arguments and loops of `tools/scev/fixture.ll`, printing `SCEV::print` and the type. The oracle prints the pinned version (`llvmpin.py` once it is on main).

## 6. Order, dependencies, peers

1. L1 (this branch continues into it), with the adapter plan above.
2. S1 then S2 (needs `constantrange.rs` from #2143) then S3: SCEV exists, no consumer.
