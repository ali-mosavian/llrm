# 386 addressing in real mode, behind the 67h prefix

The `67h` address-size prefix gives real-mode code the full 386 addressing
forms: any 32-bit register as base, a scaled index at 1, 2, 4 or 8, and a
32-bit displacement. All of it is available to the code BC emits.

What it does not give is reach. The effective address is still checked
against the real-mode segment limit of 64K, and an address above `0FFFFh`
raises `#GP`, vector `0Dh`. The prefix buys forms, not range.

The whole megabyte is still addressable, because the segment base and the
effective address compose: linear is `seg << 4` plus an EA of at most
`0FFFFh`. So a scaled-index operand works anywhere in the 1MB, as long as
each access stays inside its own 64K window.

Measured under Bochs 3.0, `cpu: model=pentium`. Sources in `docs/machine/a32/`.

## The limit

`ds = 0`, one 32-bit offset per row (`docs/machine/a32/v.asm`):

| operand | result |
| --- | --- |
| `[0]` | `5Ah`, the marker written there |
| `[0FFFFh]` | `00h`, the last byte of the segment |
| `[10000h]` | `#GP 0Dh`, one byte past |
| `[80000h]` | `#GP 0Dh`, 512K, inside the 1MB |
| `[0FFFFFh]` | `#GP 0Dh`, the top of the 1MB |

The boundary is exactly 64K, and 512K faults as surely as 1MB does. A flat
32-bit offset does not reach the megabyte from a zero segment.

The fault is `#GP` and not `#UD`: the two handlers are separate in the test
and the vector is printed, rather than assumed from the fact that something
went wrong.

## The reach

Markers written the plain 16-bit way, read back through a segment with
32-bit forms (`docs/machine/a32/x.asm`):

| operand | linear | result |
| --- | --- | --- |
| `1000:[eax]` | `10000h` | `11h` |
| `5000:[eax+esi*4+1234h]` | `51234h` | `22h` |
| `5000:[eax+esi*4]`, `esi = 48Dh` | `51234h` | `22h` |
| `9000:[ebp+edi*8]`, `ebp = 8000h` | `98000h` | `33h` |
| `f000:[ebx]`, `ebx = 0FFFFh` | `0FFFFFh` | `03h` |

The third row reaches `1234h` by scaling alone, which is the form worth
having. The last reads ROM and returns `03h` rather than the `44h` the
setup tried to write there, so it is the BIOS byte and not an echo of the
test.

`ebp` as a base defaults to `SS`, as it does in 32-bit code. Every row here
carries an explicit segment override, so that default never applies.

## Any register as a base

This is the part that pays here, more than scaling does. 16-bit addressing
offers eight operands and no others: `[bx]`, `[bp]`, `[si]`, `[di]`, and
`bx` or `bp` plus `si` or `di`. There is no `[ax]`, no `[cx]`, no `[dx]`. A
value that needs to address memory has to be moved into one of four
registers first, and BC emits exactly that move -- `mov bx,ax` ahead of the
access -- all through the corpus.

Behind `67h` every general register is a base. Markers `B0h` through `B7h`
at eight consecutive offsets, read back one per register (`docs/machine/a32/y.asm`):

| base | result | base | result |
| --- | --- | --- | --- |
| `[eax]` | `B0h` | `[esp]` | `B4h` |
| `[ecx]` | `B1h` | `[ebp]` | `B5h` |
| `[edx]` | `B2h` | `[esi]` | `B6h` |
| `[ebx]` | `B3h` | `[edi]` | `B7h` |

Each returns its own marker, so the register is the base rather than
something that happened not to fault. `esp` included, which 16-bit
addressing cannot express at all.

The prefix costs a byte and saves the move:

```
268A07              mov al,[es:bx]                  3
26678A00            mov al,[es:eax]                 4
89C3                mov bx,ax                       2
```

Addressing through a value already in `ax` costs 5 bytes and a clobbered
`bx` the 16-bit way, or 4 bytes and no clobber with the prefix.

That removes a register class rather than adding one. `regalloc.colour()`
currently refuses to put a value used as a base anywhere but `bx`, `si` or
`di`, because `select.py` cannot encode `[dx]` -- which is true only while
the operand stays 16-bit. Emitting the prefix makes every register
addressable and the constraint goes away.

## Where it is not a substitution

A 16-bit effective address wraps inside the segment; a 32-bit one does not.
`bx = 0FFFFh`, `si = 10h` (`docs/machine/a32/z.asm`):

| operand | result |
| --- | --- |
| `[es:bx+si]` | `77h`, the byte at `000Fh` -- the sum truncated to 16 bits |
| `[es:ebx+esi]` | `#GP 0Dh` -- `1000Fh` is past the limit |

So swapping one form for the other is not a rewrite of the same address.
Two things have to hold before a 32-bit operand may stand in for a 16-bit
one, and neither is free:

**The address must be provably within `0FFFFh`.** Where the 16-bit form
wrapped, the 32-bit form faults. A near fixed array with a known base and a
bounded subscript satisfies this by construction; an arbitrary computed
index does not.

**The base register's high half must be provably zero.** BC never writes it
-- its code is 8086 -- but this pass does: a widened pair leaves a real
32-bit value in `eax`. Reaching through `[eax]` after that addresses
whatever the long happened to be. The obligation is on whoever picks the
base, which is why the safe first use is a register this pass chose itself
rather than one BC left lying there.

## Encodings

```
678A00              mov al,[eax]
678A84B034120000    mov al,[eax+esi*4+1234h]
678A44FD00          mov al,[ebp+edi*8]
678A840900001000    mov al,[ecx*2+100000h]      ; #GP: the displacement alone is past the limit
```

nasm encodes `ecx*2` as base plus index at scale 1 -- `ecx+ecx` -- which is
the same effective address in two SIB bytes rather than one form. Worth
knowing when diffing against another assembler's output.

## Two things that are not this

**Above the megabyte.** `seg << 4` plus offset tops out at `0FFFF0h +
0FFFFh`, which is `10FFEFh`. An 8086 wraps that to `0FFEFh`; a 286 or later
with A20 enabled does not, and reaches the HMA. Under Bochs, `ffff:0010`
returns `00h` rather than the `5Ah` marker at linear zero, so A20 is on and
the access genuinely lands at `100000h`. A read that merely fails to fault
says nothing about which byte it found -- the marker is what makes it
decidable.

**Unreal mode.** Loading a descriptor with a 4GB limit and returning to real
mode lifts the 64K check, and the limit survives reloading the segment
register with 0 in real mode (`docs/machine/a32/w.asm`): `[80000h]` reads `00h` and
`[0FFFFFh]` reads `03h`, the same ROM byte `f000:ffff` gives. That is a
different execution mode, not something the prefix does, and nothing here
depends on it.

## What this means for the pass

Two things, and the smaller one is the scaling. BC computes an element
address with a shift, a move and an add, and a scaled-index operand folds
all three into the access that follows -- `docs/roadmap.md` lists that
against `addrm`, `arridx` and `matrix`. Nothing about real mode prevents
it, provided each access stays within its segment, which for a near fixed
array it does by construction.

The larger one is that any register can address memory. BC moves a value
into `bx` before reaching through it because 16-bit addressing leaves it no
choice, and the allocator inherits the same four-register constraint.
Both go away for a byte.

The cost is the target CPU. BC's own output runs on an 8086; anything
carrying a `67h` prefix requires a 386. That is the same trade `66h` widening
already makes, and it is made once for the whole pass rather than per site.

## Reproducing

```bash
cd docs/machine/a32 && nasm -f bin x.asm -o x.img
python3 -c "d=open('x.img','rb').read(); open('fd.img','wb').write(d + b'\x00'*(1474560-len(d)))"
bochs -q -f bochsrc
```

Output arrives on port `0E9h`, which `bochsrc` enables. The images are boot
sectors: no DOS, no BIOS calls beyond the interrupt table, so nothing between
the instruction and the answer.
