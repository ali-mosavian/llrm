## alias

Source: [`crates/opt/llrm-analysis/src/alias.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/alias.rs)

Strong, flow-sensitive alias analysis: what each pointer may point to, what
escapes and when, and what each call reads and writes.

### How it works
One vocabulary serves every frontend. A pointer's fact is a `Provenance`: a
set of `Slice`s (a canonical object, a byte range of it, a stride and an
access width) plus `restrict` roots. Objects are the function's own
(`memory::object_of`: frame `alloca`s, globals), each pointer parameter's
`Parameter` object (offset 0; a `noalias` parameter is also a restrict
root, `seeds`) and, for a call whose callee returns `noalias`, a fresh
`Allocation`. Unknown stores kill spill facts; they never manufacture a
disjointness proof.

Value solve (`point_values`). Pointer facts flow forward over the CFG to a
fixed point:

- `alloca`, `bitcast`, `addrspacecast`, `getelementptr` give a fact from
  their operand (`_direct`); a constant displacement shifts the slices, a
  variable index widens to the whole object.
- A `phi` or `select` joins its arms as a union; a pointer with an arm no
  fact follows is `UNKNOWN`.
- Pointers stored to an exact slot (a spill slot) are tracked per block in a
  `CellMap` keyed by `CellKey`; a possibly overlapping store or an unmodeled
  call write kills them; a join keeps a cell only if every parent holds it.
  A load of a pointer reads the cell, else the union of every pointer ever
  stored into the object.
- A loop-carried fact is widened to whole objects (`_widened`) at a
  natural-loop header so it settles, and a fact with more than
  `MAX_FIELDS_FOR_FIELD_SENSITIVE` slices is also collapsed, as gcc and LLVM
  do.
- Integers carry no provenance: a `ptrtoint` publishes its pointer, as LLVM
  counts it a capture, and an `inttoptr` has none.

```text
 %p = alloca [8 x i16]            %p -> {frame:%p [0,16)}
 %q = gep %p, i16 2               %q -> {frame:%p [4,6)}
 store ptr %q, ptr %slot          cell(%slot) = %q          (spill slot)
 %r = load ptr, ptr %slot         %r -> {frame:%p [4,6)}    (exact slot)
 call @unknown(ptr %q)            %q's object escapes from here on
```

Escape solve (`points_to`, `escapes`). Over the value solve, a forward
gen/kill dataflow finds what has been published, per instruction
(`EscapedBefore`): objects handed to a call that keeps them (not
`nocapture`; a summary's `captures` stand where the callee has one), stored
somewhere other than a frame, returned, or converted to an integer something
reads, closed over pointers stored in what was published and over the
initializers of published globals. A frame object not escaped before an
access cannot be reached by a pointer no fact follows
(`EscapedBefore::apart`, LLVM's `EarliestEscapeInfo`).

Summaries (`summaries`). Each body's `Summary` is the slices it reads and
writes, whether it reads or writes unknown memory, its captured parameters,
and the `!tbaa` types of its unplaced writes. It starts from the body's own
accesses (`_direct_summary`) and adds each callee's summary instantiated at
the call's actual arguments (`instantiated`), to a fixed point over the call
graph in SCC order; a cycle is solved from nothing, so a recursive function
that captures nothing proves so. A callee with a body that may be replaced
(weak or linkonce) describes no call. A call to something with no summary
reaches what its attributes allow (`_allowed`: `memory(...)`, `readnone`,
...): through each actual the objects it points to, elsewhere the nonlocal
memory, what escaped before the call, and, of the globals
`crate::globalsaa` tracks, those it names; unless `nocallback` it also
does what the module's entry points do (`callbacks`). `summaries_updating`
redoes only the bodies that changed and their readers.

Call effects (`calls_annotated`). Each call gets an `Effect`: the `MemRef`s
it loads and stores, instantiated through the actuals, and the bytes it
fills (`initialized`: bytes written before any is read). It is a side table,
because the rich MIR's call carries no memory operands.

Access annotation (`annotated`). Each load and store gets its provenance;
where a range bounds its index the slice narrows to the bytes the index can
reach, using strides from `congruences` (a value's residue modulo a
modulus). Far or fixed-address accesses name linear memory.

### Provides
`pointers`, `point_values`, `points_to` and `PointsTo` (`values`, `escaped`,
`escaped_before`, `nonnull`), `seeds`, `summaries`, `calls_annotated`,
`annotated`, `congruences`, `initialized`, `read_arguments`,
`nonnull_by_definition`. Manager entries in `crate::manager`: `Pointers`,
`PointValues`, `Annotated`, `CallEffects`, `Summaries`. Consumers:
`crate::memory` (a `Unit`'s lazily built `annotated` and `points_to`),
`crate::memoryssa` (`calls_annotated`), `crate::avail`
(`EscapedBefore`), `crate::observers`, `crate::induction`
(`congruences`), `crate::globalsaa`, `crate::interprocedural`, and
`gvn`, `promote`, `loadjoins` and `decide` in `llrm-transforms`.

### Needs
`crate::globalsaa` (tracked globals), `crate::cfg::Shape`,
`crate::ranges` and `crate::consts` (index intervals, constants),
`crate::cellmap`, `crate::induction` (strides), `llrm_mir::memory` for
what attributes state.

### See also
LLVM `BasicAA`, `GlobalsAA`, `EarliestEscapeInfo`, `FunctionAttrs`
`initializes`; GCC `tree-ssa-structalias.cc` (field sensitivity cap).

## assumptions

Source: [`crates/opt/llrm-analysis/src/assumptions.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/assumptions.rs)

What each block assumes, as LLVM's AssumptionCache: the conditions of the
`llvm.assume` calls in it.

### How it works
`Assumptions::of` walks the body once and records, per block, the first
operand of every call to the `Assume` intrinsic, in program order.

`here(at)` returns what block `at` itself assumes. `above(shape, at)` climbs
the immediate-dominator chain from `at` and returns what each strict
dominator assumes, nearest block first and the last assume of a block
first.

```text
 b0: assume(c0)            above(b3) = [c1, c0]
  |
 b1: assume(c1)            here(b3)  = [c3]   (not in above(b3))
  |
 b3: assume(c3); use
```

A block's own assumes are not part of `above` for that block, so a use
before an assume in the same block is not covered by it. The caller reads
`here` for the part of the block it is in. `above` returns early when no
block assumes anything.

### Provides
The assumed conditions per block. Consumers: `crate::guards` turns them
into `Guard`s, and `crate::ranges` narrows value ranges with them. The
manager entry is `crate::manager::AssumptionCache`; a `Unit` without one
builds its own on first ask, which `built()` counts for tests.

### Needs
`crate::cfg::Shape` for the dominator tree.

### See also
LLVM `AssumptionCache`.

## avail

Source: [`crates/opt/llrm-analysis/src/avail.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/avail.rs)

Available loads and dead stores, as LLVM's GVN load forwarding and DSE find
them through MemoryDependence.

### How it works
Two independent queries share the memory model (`MemRef` cells and
`crate::memoryssa`'s `Accesses`).

Forwarding. `forwardable_walk` takes a set of loads and, for each plain
(non-volatile) load, asks MemorySSA for the nearest writes that may clobber
its bytes and tries three sources in order:

1. One clobber that is a plain store to the same bytes, defined before the
   load, whose value has the load's type: the load is that value.
2. Two or more clobbers (at most `MAX_NEAREST_WRITES`) that are all exact
   stores of one value defined where the load can read it, such as the arms
   of a join that each stored the same thing.
3. A dominating load of the same bytes, nearest first, with nothing between
   the two that may change them (`MemorySSA::unchanged`). A candidate whose
   walk fails also fails every load that dominates it.

A value serves a read only of its own type. Each answer is a `Forward { at,
value }`.

```text
   store i32 %v, p          %a = load p     <- 1: %a is %v
   ...                      ...
   %a = load p              %b = load p     <- 3: %b is %a
   ...
   br c, T, F      T: store %v, p   F: store %v, p
   J: %b = load p                                 <- 2: %b is %v
```

Dead stores. `dead_stores` is a backward must-overwrite analysis over the
CFG. Every cell a function stores to is numbered once (`Stored`), as LLVM's
DSE numbers its memory locations, and a block's state is a set of numbered
cells overwritten before any read. Walking a block backward:

- a plain store whose cell is covered by one overwritten cell, or whose
  bytes the overwritten cells together write (`pieced`), is dead; the cell
  then joins the set;
- an instruction that reads or writes anything else removes the cells it may
  touch (`clobber`, using `may_clobber` and `EscapedBefore` where given);
- a fill (what a call writes before it reads) adds its cells.

At a join the state is the intersection over the successors, computed per
cell with "some cell naming the same bytes" (`alike`) so a spelling
difference does not lose it. The fixed point starts from every stored cell
and shrinks, with a worklist in postorder, and only the last verdicts stand.
A block with no successor starts from nothing, since the caller may read the
cell; with `private` (a predicate for cells nothing outside the function can
read) it starts from the private cells; a block ending in `unreachable`
starts from every cell. A call whose accesses are not known keeps only the
private cells in the set (nothing but a named access can read those); any
other unknown instruction empties it.

Cells that share bytes share an overlap bucket (`regions`), so a cell is
compared with its bucket and not with all cells.

### Provides
`forwardable_walk`, `dead_stores`, `dead_stores_escaping`, and the
accessors `loaded_into`, `stored_from`, `stored_cell`. Consumers:
`transform` (load forwarding), `loadjoins` and `dse` in `llrm-transforms`.

### Needs
`crate::memoryssa`, `crate::alias` (`EscapedBefore`), `crate::ranges`
(register constants), `crate::cellmap`, `crate::regions` and
`crate::cfg`.

### See also
LLVM `MemoryDependenceAnalysis`, GVN `processLoad` and
`DeadStoreElimination`.

## branchprob

Source: [`crates/opt/llrm-analysis/src/branchprob.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/branchprob.rs)

Static branch probabilities and block frequencies, as LLVM's
`BranchProbabilityInfo` and `BlockFrequencyInfo` estimate them when no
profile says otherwise.

### How it works
`estimated` gives every edge a probability and every block a frequency. A
block with one successor takes 1. A block with several takes the first
heuristic that tells its successors apart, in this order (`Heuristic`
records which one fired):

1. `Declared`: `!prof` `branch_weights` on the terminator, one per named
   target, summed per distinct successor. Weights that do not name every
   target, or sum to zero, say nothing.
2. `Invoke`: an invoke's unwind edge is taken 1 in 2^20.
3. `Unreachable`: a successor every path of which ends in `unreachable`, a
   `noreturn` call or a `cold` call (`noreturn::cold`) is all but never
   taken.
4. `Loop`: in a loop, staying is 124 to 4 for leaving (`LOOP`, LLVM's
   weights).
5. `Counted`: a branch on a compare of the counters of an enclosing loop
   whose trip count induction proved (`trips`, at most 4096). The counters
   (header phis from a constant start) are stepped trip by trip and the edge
   is taken on the share of trips the compare holds on, clamped away from 0
   and 1.
6. `Pointer`, `Zero`, `Float`, from the compare feeding a `br`: `p == q` on
   pointers fails (20:12), as do `x == 0`, `x == -1`, `x < 0` and `x <= 0`
   on integers, and `x == y` on floats; `isnan` (`uno`) is 1 in 2^20. Truth
   values (0 or all ones, 0 or 1, a compare, or a call whose `range` says
   so), one-bit tests (`x & 2^n`) and the sign of a three-way compare are no
   quantity and say nothing.
7. `Call` (GCC, from Ball and Larus; LLVM has no such heuristic): a
   successor that calls, where the other does not, is not taken (67:33).
8. `Return` (GCC): a successor that returns, where the other does not, is
   not taken (66:34); where it only returns a constant, 98% not taken if
   negative, 71% if null, 65% if another constant (`PRED_NEGATIVE_RETURN`,
   `PRED_NULL_RETURN`, `PRED_CONST_RETURN`).
9. `Even`: equal weights.

Frequencies are relative to the entry's 1 (`propagated`). Blocks go in
reverse postorder and a block's frequency is the sum over its non-back edges
of predecessor frequency times edge probability, times its loop's scale if
it is a header. A loop's scale is 1 / (1 - p), `p` the probability of coming
back round, capped at 4096 (`LOOP_SCALE`, LLVM's cap). Inner loops are
scaled first. With proven trips the scale is the trips (or trips + 1 when
the only exit is a test at a non-latch header), and the exit test takes `1 /
(trips + 1 - tested)` of the mass, so the trips stay.

```text
 entry 1 --> H (scale 1/(1-0.969) = 32) --> body --+
              ^                                     |  stay 124/128
              +-------------------------------------+
              |
              +--> exit: 1   (entering once)
```

The propagation takes edge probabilities as a function, so the backend uses
it too (`propagated_edges`, `Cycle`) and MIR and LIR estimates agree.

### Provides
`Odds { taken, frequency, by }` from `estimated`, `propagated` and
`propagated_edges`, and the constants `LOOP` and `LIKELY` (0.8, the edge
probability above which machine block placement trades the shorter layout
for it). Consumers: `profit` and `rotate` in `llrm-transforms`; the
backend's `isel`, `jumps` and `analysis/frequency` (grep `branchprob::`).

### Needs
`crate::cfg::Shape` for loops, `crate::noreturn` (`terminal_sites`,
`cold`), `crate::effects::Declarations` and the trip counts the caller
takes from `crate::induction`.

### See also
LLVM `BranchProbabilityInfo.cpp`, `BlockFrequencyInfo`; GCC `predict.def`.

## cellmap

Source: [`crates/opt/llrm-analysis/src/cellmap.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/cellmap.rs)

A map from memory cell to fact, indexed by the object each cell lies in, so
a write is tested only against the cells it can reach.

### How it works
`CellMap<K, V, B>` keeps `K -> V` items in insertion order and groups the
keys into buckets `B` (a `Bucket`: the object, or the object's part, a cell
lies in). The caller hands `insert` each new cell's bucket and, if it has
one, its byte span; the map never recomputes them, so a cell's bucket must
not change while the cell is held. Cells with a span are also kept sorted
by start, per bucket (`Spans`), with the widest span ever held as a bound
on how far below a write an overlapping cell can start.

```text
 CellMap
  items    k0 -> v0, k1 -> v1, k2 -> v2          (insertion order)
  buckets  objA: {k0, k2}   objB: {k1}
  spans    objA: [(low=0,k0) (low=8,k2)]         sorted by start
  parts    bucket index by component (`Bucket::held` / `released`)

 kill(reached = [objA], overlaps, displaced = (objA, [4,12))):
   asks `overlaps` only of cells in objA whose bytes meet [4,12)
```

`kill(reached, overlaps, displaced)` deletes every cell a write may reach.
`reached` names the buckets to look in (all when `None`); `overlaps` is the
exact test, asked only of the cells the index returns; `displaced` limits
those further, in the buckets it names, to cells whose span meets its span.
`asked` returns the same candidates without deleting. The index may only
skip work: under test a flag makes `kill` ask the exact test of every cell
it skipped.

### Provides
The container. Consumers: `crate::alias`, `crate::consts`,
`crate::avail`, `crate::regions` and `promote` in `llrm-transforms`.

### Needs
`crate::regions::ByteRange`.

## cfg

Source: [`crates/opt/llrm-analysis/src/cfg.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/cfg.rs)

A function's blocks as the graph walks see them: block ids, successors,
dominance, natural loops and reachability, built once per body.

### How it works
`graph` turns a `Function` into `Block { at, succ }`s, one per block in
layout order, the entry first, so the walks of `crate::graph::loops` run
on the rich MIR. `successors_of` and `predecessors_of` answer for one block
without building the whole graph, and the `Around` trait does the same for
a `Loop`: `entering` (outside blocks that name the header), `exits` (edges
leaving the body) and `preheader` (the single entering block whose only
successor is the header). Building the graph per loop made a function of N
loops cost N^2.

`Shape` bundles what the passes ask of a body:

```text
 Shape
  +- dominance: Dominance   over llrm_mir Dominators; reachable, dominates,
  |                         immediate, depths, frontiers, irreducible
  +- loops: Vec<Loop>       from llrm_mir Loops, ids not BlockIds,
  |                         inner loops first
  +- reaching: Reaching     blocks with a path to a block, found on ask
                            and cached
```

`Dominance` treats an unreachable block as dominated by nothing and
dominating nothing. `dominates` and `depths` answer without building each
block's full dominator set (`dominators`, quadratic in a chain of
diamonds). `natural` orders loops by body size, inner first.
`Reaching::to` walks predecessors from the target and returns the cached
set on a second ask.

`_unreachable` deletes blocks the entry does not reach, trims phi inputs of
removed edges, and replaces uses of values defined in dead blocks with
poison before erasing them.

### Provides
`Shape` (a `Analysis` named `shape`), the
`Dominance` and `Reaching` types, and the id/graph helpers. Consumers:
nearly every loop pass and analysis in `llrm-transforms` and this crate,
and the backend driver and isel (grep `cfg::Shape`, `cfg::id`).

### Needs
llrm-mir's `Dominators` and `Loops`.

### Keeps
`Shape` is preserved when it is kept, or when both `Dominators` and `Loops`
are. It does not read the outer (module) analyses.

## constant_cycles

Source: [`crates/opt/llrm-analysis/src/constant_cycles.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/constant_cycles.rs)

Sparse value propagation over phis, with distinct pending and overdefined
states, to find constants that only a cycle proves.

### How it works
Each value has a state: `Pending` (nothing met yet), `Known(fact)` or
`Overdefined`, with `Pending` the identity of the meet and two different
facts meeting to `Overdefined`. `propagated(unit, seeds, successors)` takes
the facts already known (`seeds`, from `crate::consts`) and settles the
rest, which are the phis no seed has and the operations that depend on
them. A body with no such open phi returns its seeds at once.

A worklist re-evaluates a value when one of its inputs changes. A phi meets
the facts of its incoming values (constants evaluate through
`consts::_operand`); a supported operation (a foldable binary operation,
`trunc`, `sext`) folds through `consts::_result` when every input is known,
stays pending while some input is pending and none is overdefined, and
otherwise is overdefined. When nothing is left on the worklist and pending
values remain, they are made overdefined and propagation continues.
Pending is never read as LLVM `undef`: an unresolved value is overdefined
before the result is returned.

```text
 b1:  %i = phi [0, b0], [%j, b1]    %i: meet(Known 0, pending) = Known 0
      %j = add %i, 0                %j: Known 0
                                    %i again: meet(Known 0, Known 0), stable
```

An optional successor evaluator (`Successors { choose, reads }`) finds the
executable edges. Only the entry is live at first; a block's `choose`
answers which successors run from the facts so far, and is asked again only
when a value in `reads` for that block changes. A phi then meets only the
incoming values of executable edges, and the entry's phis also meet
`Overdefined`, since the entry runs before any back edge. A block whose
branch `choose` defers (`None`) keeps every successor once nothing else is
left to resolve.

### Provides
`State`, `Successors` and `propagated`. Consumers: `crate::consts`
(`known`, with no evaluator) and `decide` in `llrm-transforms`, which
passes an evaluator to find which branches fold.

### Needs
`crate::consts` for the per-operation folding, and `crate::cfg`.

### See also
LLVM SCCP (`SCCPSolver`) and its `unknown`, `constant`, `overdefined`
lattice. `LLRM_CHECK_CYCLES` re-derives the result without the early
return and asserts it matches.

## consts

Source: [`crates/opt/llrm-analysis/src/consts.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/consts.rs)

Which values are known, and what they are: integer constant propagation and
folding, with memory read through MemorySSA.

### How it works
A fact is `Known { n, width }`: the low `width` bits of the value are `n`,
nothing is said above them. An operation folds only where the widths
agree (`_result`): integer `add`, `sub`, `mul`, `and`, `or`, `xor`, shifts,
divisions that do not fault (`folds`), `sext`, `zext`, `trunc`, `icmp`
(`holds`), `x ^ x` and `x - x`, the fixed-point intrinsics, and a pointer
compare of two addresses of one global. A width is in bits; a memory
cell's, in bytes.

Registers. `known` runs a fixed point over the body in layout order: each
integer result not yet known is folded from the facts so far, and a phi
is known where every incoming value is known and they agree. It then
hands the facts to `crate::constant_cycles`, which settles the phis whose
incoming values depend on each other around a loop.

Memory. `known_walked` starts from the register facts and, for each load,
asks `crate::memoryssa` which stores reach it (`load_providers`). If
they all put the same number in the bytes the load reads, so does the
load (`provided`; a store may serve a load of another type, or several
stores serve one byte at a time). No state is held per block, so the cost
is the walks, not cells times joins. A load whose index only memory taught
is asked again with the index placed, up to four rounds. `known_walked_over`
adds what counted float loops leave in memory at their exits
(`crate::floatfacts`).

```text
   store i16 7, @g          known:        %a is not known
   %a = load i16, @g        known_walked: %a = 7, %b = 8
   %b = add i16 %a, 1       (the walk finds the store)
```

The caller states what each call writes (`Calls`, from
`alias::calls_annotated`); a call not listed writes what
`memory::unmodeled_write` says. A far store through a segment selector
nothing yet resolves is taken to write no program object, and the solve is
made again without any such selector that did not resolve to a number.

`memory_queries` and `_MemoryQueries` answer alias questions about the cells
of one solved epoch, each cell carrying its object, for passes that walk
instructions with a fact table (`crate::cellmap` indexes the cells by
overlap bucket).

### Provides
`Known`, `known` (registers, cached as `crate::manager::Registers`),
`known_walked` and `known_walked_over` (memory; cached as
`crate::manager::ThroughMemory`), `memory_queries`, `holds`, `folds`.
Consumers: `gvn`, `algebraic`, `fold`, `decide`, `unswitch`, `floatloop` and
`interprocedural` in `llrm-transforms`, the backend's `isel`, and most
analyses of this crate.

### Needs
`crate::memoryssa`, `crate::alias` (the call table), `crate::ranges`,
`crate::regions`, `crate::cellmap`, `crate::constant_cycles`.

### See also
LLVM `SCCP`/`ConstantFolding`; GCC FRE walks the same virtual use-def chain
for a load's value (`vn_reference_lookup`). `LLRM_CHECK_CYCLES` in
`crate::constant_cycles`.

## demanded

Source: [`crates/opt/llrm-analysis/src/demanded.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/demanded.rs)

Which bits of each integer value anything reads: LLVM's `DemandedBits`.

### How it works
A backward fixed point over the use-def graph, the dual of
`valuetracking::known_zero`. A bit no user reads can be anything, so a mask
that clears only such bits, or an operand all of whose bits are such,
can go.

Every instruction that is not a pure integer operation reads its integer
operands in full: stores, calls, compares, divides and pointer
computations. Those seed the map. A pure integer instruction (a phi, or one
`valuetracking::demanded_operands` has a rule for) passes on instead: given
the bits read of its result, the rule gives the bits read of each operand,
and those join into the operand's entry.

```text
  %a = load i32          read: 0x000000ff   (only the low byte)
  %m = and i32 %a, 255   read: 0xffffffff   <- stored in full
  store i32 %m, ptr %p

  and passes on 0xff & 0xffffffff = 0xff to %a
```

Work goes onto a stack whenever an entry grows, so a loop's phis reach a
fixed point: demand only grows and is bounded by the width.

Only integers of at most 128 bits are tracked (`u128` masks). A value that
is absent from the map is not read at all.

### Provides
`demanded(context, function)`: a `ValueId -> u128` map. Cached as
`crate::manager::DemandedBits`. Consumer: `algebraic`'s removal of masks
and operands over unread bits (`algebraic` in `llrm-transforms`).

### Needs
`llrm_mir::valuetracking::demanded_operands`, the per-opcode table.

### See also
LLVM `DemandedBits` and `SimplifyDemandedBits`.

## dependence

Source: [`crates/opt/llrm-analysis/src/dependence.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/dependence.rs)

Data dependence distances over a two-deep loop nest, and the outer unroll
factor that unroll-and-jam may use for them.

### How it works
An `Access` is one memory reference of the nest body: an object, a list of
`Subscript`s (`constant + outer * i + inner * j`, `i` and `j` the iteration
numbers; `a[i][j]` has two, a flattened address one), loop-invariant
`symbols`, a width and a write flag. The caller has found the objects.

`distances(first, second, limit, inner_trips)` solves
`outer * x + inner * y = constant difference` in each subscript, in both
directions, for outer distances `x` in `0..=limit` and one inner distance
`y`. Pairs with different objects are `Independent`. Pairs whose symbols,
width or coefficients differ are `Unknown`. Otherwise the result is the
lexicographically non-negative `(x, y)` vectors, with `y` bounded by
`inner_trips` where known. A reference no subscript moves with in the inner
loop repeats at `(x, 0)` and, for `x = 0`, `(0, 1)`.

`factor(accesses, max_unroll, min_percent, inner_trips)` looks at every pair
of accesses. Unrolling the outer loop by N turns `(x, y)` into `(x / N, y)`,
so a vector bounds N when it would reorder the pair in the fused loop:

```text
 for i                     for i step N
   for j        ==>          for j
     S(i, j)                   S(i,j) S(i+1,j) ... S(i+N-1,j)

 vector (x, y) ok if x >= N, or y > 0; y = 0 with x < N needs two reads or
 two accesses that both vary with j; else N is capped at x (y < 0).
```

Two reads never order anything; an `Unknown` pair with a write gives
`unroll = 0`. `profit` is one more than the largest outer distance at which
a reference repeats at `y = 0` (copies that make it go away), `removed`
counts such vectors, and the factor is refused (`profit = 1`) if
`removed * 100 / accesses` is below `min_percent`. `min_percent = 0` applies
always, with at least 2. The result is `min(unroll, profit, max_unroll)`.

### Provides
`distances`, `factor`. Consumer: `unroll_jam`
(`crates/opt/llrm-transforms/src/unroll_jam.rs`).

### See also
gcc `tree-data-ref.cc` distance vectors read by `adjust_unroll_factor`
([`gimple-loop-jam.cc:403`](https://github.com/gcc-mirror/gcc/blob/releases/gcc-13.4.0/gcc/gimple-loop-jam.cc#L403)),
`tree_loop_unroll_and_jam`
([`gimple-loop-jam.cc:504`](https://github.com/gcc-mirror/gcc/blob/releases/gcc-13.4.0/gcc/gimple-loop-jam.cc#L504));
LLVM `DependenceAnalysis` and `LoopUnrollAndJam`.

## difference

Source: [`crates/opt/llrm-analysis/src/difference.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/difference.rs)

What a set of compares proves of the unknowns they test, by difference
bounds: LLVM's ConstraintElimination.

### How it works
Each side of a compare is a `Scev` that is one unknown plus a constant
offset, or a constant. A compare of two sides is a constraint
`x - y <= c`. `proves` builds a graph with one node per unknown plus node 0
for the constant zero (`Z`), puts the constraints in as edges, and closes it
with Floyd-Warshall so `dist[a][b]` is the most `a - b` can be. The asked
compare holds when the closure bounds its `left - right` tightly enough.

```text
  facts:  x < y        y - x <= -1      node y --(-1)--> node x
          y <= 10      y - Z <= 10      node y --(10)--> Z
  asked:  x < 11       x - 11 <= -1     closure: x - Z <= (x - y) + (y - Z)
                                                   <= -1 + 10 = 9  -> holds
```

Other facts the system takes in:
- A stated range `[low, high]` of an unknown bounds it against `Z`.
- Unsigned compares. An unsigned compare is a signed one where both sides
  are known non-negative. `small[n]` marks unknowns that are: `Z` itself, an
  unknown whose stated low is at least 0, a `x <u y` with `y` non-negative,
  and any unknown the closure bounds below by zero (the closure is then run
  again, at most four rounds). Unsigned facts that are not so are ignored,
  as are `ne` facts.
- A negative cycle means the facts contradict each other: everything is
  proved.

An offset side is trusted only if the closure keeps `unknown + offset`
inside the signed range, so the sum cannot wrap; an unsigned goal also needs
both sides' least value to be at least zero. Facts with an offset on an
unknown are dropped (only offset-free sides state a fact), and a system
with more than 24 nodes (`MOST_NODES`; the closure is cubic) proves
nothing. The answers: `slt`/`ult` is `left - right <= -1`, `sle`/`ule` is
`<= 0`, `sgt` and `sge` swap the sides, `eq` is both ways, `ne` is either
way strictly.

### Provides
`proves(width, facts, ranges, predicate, left, right)`. Its one consumer is
`crate::guards` (`Given::holds`), which supplies the guards and the
declared ranges.

### Needs
`crate::guards::Guard`s and `crate::induction`'s `Scev` and `Monomial`.

### See also
LLVM `ConstraintElimination`.

## floatbounds

Source: [`crates/opt/llrm-analysis/src/floatbounds.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/floatbounds.rs)

Floating operations that are exact over bounded, not necessarily known,

### How it works
`exact(unit, constants)` returns the float instructions proven numerically
exact: every value they can produce is an integer of magnitude at most 2^24
(`binary32`) or 2^53 (`binary64`), so conversion and the arithmetic stay
exact. It is interval arithmetic over the same `Rule`s as
`crate::floatfacts` (`evaluated` on `(low, high)` pairs: `Neg` flips,

and `Sqrt` have no rule) and fails closed where the result leaves the
format's exact range.

Operands. An integer input is its whole type range. A float is bounded where
floatfacts knows it as an integer constant, or where it was bounded in an
earlier round. A float phi is bounded by the union of its incoming bounds.
Memory: for a load, `_memory` bounds every element it may read, from the
index's interval times its scale (at most 64 elements) and the cell facts at
the load (`floatfacts::cells_before`).

The pass iterates to a fixed point, each round bounding phis and then trying
every pending instruction, so a result proven in one round feeds the next.

```text
   %i  in [0, 100]             int input: its interval
   %f = sitofp i16 %i          Convert      -> [0, 100]
   %g = fmul double %f, %f     Mul          -> [0, 10000]  < 2^53: exact
   %h = fadd double %g, 0.5    0.5 not an integer: not exact
```

`exact`, `evaluated`, `_memory`. No pass consumes them: only this module's
tests call them, and `exact` fails unless the caller supplies the loop
bounds in `Unit::bounds`.

`crate::floatfacts` (`rule`, `Format`, facts and `cells_before`),

## floatfacts

Source: [`crates/opt/llrm-analysis/src/floatfacts.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/floatfacts.rs)

Exact finite values of floating-point operations, and the memory they pass
through.

### How it works
A fact is `Finite { value: Fraction, negative_zero }`: a result that is
exactly representable in its format. It therefore holds under any rounding
mode and any flush-to-zero, both of which are the environment's and not
stated in the rich MIR. `nsz`, the frontend's promise, lets an exact
cancellation's zero be +0; without it, a sum or difference that cancels to a
zero of unprovable sign is not a fact.

`rule(unit, inst)` gives an instruction's floating `Rule`: an `Operation`
(`Convert`, `Truncate`, `Neg`, `Abs`, `Sqrt`, `Add`, `Sub`, `Mul`, `Div`),
its operands' `Format`s (`Binary32`, `Binary64`, `Signed(w)`, `Unsigned(w)`)
and its result's. The instructions with one are the arithmetic, `fneg`,
`llvm.fabs`, `llvm.sqrt`, `llvm.lrint`, the casts, and a plain float load or
store (a `Convert` to its own format). `fptosi` and `fptoui` truncate, as
the rich MIR defines them. `evaluated(rule, inputs)` computes the result as
an exact rational and returns it only if it fits the result format (the
significand has at most 24 or 53 bits and the exponent is in range, or an
integer in range); `sqrt` needs a perfect square, `div` a nonzero divisor.

`solved_with(unit, calls)` (or `solved_over`, given the integers) is one
solve: `crate::consts`' integers through memory (`known_walked`), then the
float facts over them, in program order until nothing changes. A float phi
is known where every incoming value agrees. A float load is read from the
stores `crate::memoryssa` says reach it, as consts reads an integer one,
and a float store's bits reach its cells as a fact about the stored value
(`_with_stored`).

```text
   %a = fadd double 1.5, 2.0       Add(Binary64)   -> 3.5, exact in 53 bits
   store double %a, ptr @x         Convert         -> cell @x holds 3.5
   %b = load double, ptr @x        read from MemorySSA's providers -> 3.5
   %c = fdiv double %b, 3.0        3.5/3 = 7/6, not exact: no fact
```

Counted float loops. `loop_exits` finds two-block counted loops (a
single-latch loop whose latch ends in its `br` to the header, with a single
preheader) whose float state lives in memory. If induction proves the trip
count it replays the latch `count` times over the cells found before the
loop (`repeated`) and reports what each stored cell holds at exit as a
`LoopExit`. `cells_before` reads the cells one point holds over these facts.

### Provides
`Solved { integers, facts }`, `solved_with`, `solved_over`, `known`,
`converted` (exact float-to-integer results), `loop_exits`, `exits`,
`repeated`, `cells_before`, `touches` (whether a body has any float value; a
body with none skips the solve). The manager entry is
`crate::manager::FloatFacts`. Consumers: `floatfold`, `floatloop` and
`fold` in `llrm-transforms`; `crate::consts` takes `LoopExit`s through
`known_walked_over`; `crate::floatbounds`.

### Needs
`crate::consts`, `crate::memoryssa`, `crate::induction` (trip counts),
`crate::cfg::Shape`.

### See also
LLVM ValueTracking's `computeKnownFPClass`, narrowed to one exact value.

## frameescape

Source: [`crates/opt/llrm-analysis/src/frameescape.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/frameescape.rs)

Which frame objects' addresses reach where, and which are exposed.

### How it works
A frame object is an `alloca`, named by its result. An address moves
through `getelementptr`, `bitcast`, `addrspacecast` and `freeze` (one
operand in, one out) and through phis. Everything else that uses an address
either accesses through it or exposes it:

- a load's pointer and a store's pointer (not the stored value) are
  accesses;
- a lifetime marker (`marker` says which instructions) names an object
  without handing out its address;
- any other use, including storing the pointer, passing it to a call,
  returning it, `ptrtoint`, or comparing it, exposes it.

`exposes(function, alloca, marker)` follows the alloca's uses through moves
and answers true at the first exposing use. `exposed_allocas` does it for
every alloca in one pass: it marks each value that has an exposing use,
then propagates back along the move edges, so an address that reaches an
exposing value through moves is exposed too. `analysed` computes the same
by fixed point, as `origins` (the allocas each value may hold the address
of) and `exposed`; only tests call it.

```text
 %a = alloca            %a --gep--> %b --phi--> %c
 %b = gep %a, 4         load %b          access: not exposure
 %c = phi [%b, ..]      call @f(%c)      exposure: %a is exposed
```

`framed(function)` is the other question: which values hold an address
inside frame objects on every path, and which objects. C's pointer
arithmetic stays inside its object, so an address the body took of a local
and moved by an integer still reaches only that local's bytes. It is
optimistic: phis and moves start unrefuted, a value is refuted when it has
a non-address definition (a parameter, a load, a call) or an input that is
a number, and refutation repeats until what remains is stable.

### Provides
`exposed_allocas`, `exposes`, `framed`, `analysed`. Consumers:
`crate::memory` (`object_of` marks an object captured when exposed), the
manager entry `crate::manager::ExposedFrames`, `crate::interprocedural`
(`framed`) and the backend's `isel` (which frame objects are exposed).
`scans` counts `exposes` calls, for tests.

## generated

Random loops for checking the recurrence form (`induction::Scev`) against
the interpreter.

### How it works
A case is one counted loop over 16-bit values, built from a seed:

```text
 b0:  invariants (expressions of the arguments a b c s x and constants)
 b1:  %i = phi [start, b0], [%i + step, b1]      start: %x or a constant
      %t = phi [0, b0], [%t + 1, b1]             step:  %s or a constant
      e0 .. en  random expressions of %i and the invariants
      select chain on %which: returns ej
      br (%t + 1 <u %n), b1, b2
```

Each expression is built up to three deep from add, sub, mul, shl by a
constant, `sext`, `zext` and `trunc`, with 16- and 32-bit widths. A
`Tracked` value records its name, width and degree in the counter (0
invariant, 1 affine, more not a recurrence) and whether an extension of a
varying value is on the way (affine only where ranges say it does not
wrap). `Tracked::affine` says a recurrence form should exist for it.

Evaluating the loop with `which = j` returns `ej` on the last trip, so
`observed` runs the module in the interpreter and any value's form can be
compared with what the program computes, on inputs from `Inputs::random`.
`Rng` is xorshift64* seeded per case, so a case is the same everywhere.

Seeds are replayable: `SCEV_SEED=k` runs seed `k` alone and prints its
text; `SCEV_SEEDS=n` runs `n` seeds instead of the default.

`case`, `seeds`, `observed`, `Inputs`, `Rng`, `Tracked`, built only for

## globalsaa

Which globals no code outside the program reaches but by name: LLVM's
GlobalsAA, GCC's ipa-reference.

### How it works
A global variable is tracked when three things hold. No body in any module
lets its address escape: each body's pointer solve (`alias::points_to`)
lists the globals that escape. No live initializer holds its address (an
initializer is read only through its own global). And the program does not
export it, or the program's runtime module lists it in `!llrm.named`: the
runtime names it but never hands its address out.

```text
 module A  @g = internal global ...      tracked: no body leaks &@g
           f(): store 1, @g              reached only by its name,
           h(): call @ext()              so a declared @ext cannot touch @g
```

A tracked global is uncaptured (`memory::global_object`), so no nonlocal
reach meets it. What each body does to one, callees included, is in
`crate::alias`'s summaries. A callee no summary describes reaches the
tracked globals as `Globals::unsummarized` says:

- a body of the module (or of another module that defines this declaration):
  all of them;
- otherwise the named ones it writes (those its `!llrm.writes` node in the
  runtime module lists, or all without one) and, unless it is `nocallback`
  (`calls_back`), what the module's entry points do, as it may call back
  into them (`entries`: bodies not internal, or address-taken).

`!llrm.named = !{!0}` with `!0 = !{ptr @g, ...}`; `!llrm.writes = !{!1,
...}` with `!1 = !{ptr @routine, ptr @g, ...}`: of the named globals,
`@routine` writes by name only those listed. The runtime module's globals
stand for each module's of the same names.

Across modules, `ProgramGlobals` finds, per module, the globals another
module lets escape or holds in an initializer (`Elsewhere.escaped`), its
declarations another module defines and the functions another takes the
address of, comparing globals by the definition they resolve to. A global
passed to a callee that is `noretain` is not named for this purpose. Each
body's contribution is kept while its history is unchanged, and `covers`
says whether a held result still claims no more than a fresh one would.

`Globals` (`tracked`, `unsummarized`, `entries`, `covers`), `analysis`,
`ProgramGlobals`, and the helpers `embedded` and `calls_back`. The manager
entry is `crate::manager::GlobalsAA`. Consumers: `crate::alias`,

## guards

Source: [`crates/opt/llrm-analysis/src/guards.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/guards.rs)

What the branches that dominate a block prove on entry to it.

### How it works
`guards(unit, at)` climbs the dominator chain from block `at`, at most 64
blocks (`MAX_DOMINATORS`), and at each dominator `above` collects two
things. The first is the conditions the block assumes (`assume` calls, from
`crate::assumptions`), which hold below it wherever its terminator goes.
The second is the compare of `above`'s conditional branch, when the edge
toward `at` alone enters the block it leads to: that block dominates `at`
and every other predecessor of it is dominated by it (it is a back edge), so
the branch outcome holds on every path to `at`. A compare is read as `Guard
{ predicate, left, right }` over `Scev`s. `_proven` also opens an `and`
that is true or an `or` that is false into both parts, and flips the
predicate when the edge is the false one.

```text
   b0: br (n > 2), b1, b9          guards(b2) = { n > 2, n != 0 }
    |
   b1: br (n != 0), b2, b9         b1 and b2 each have one predecessor, so
    |                              each branch holds on every path to b2
   b2:  <- here
```

`on_edge(unit, from, to)` is the guards of `from` plus what its own branch
says of the edge to `to`. `decides(unit, facts, condition)` answers a
compare with true or false when a guard implies it or its inverse.

`implies(guard, predicate, left, right)` is direct implication: the same two
sides (either way round) under a predicate at least as strong (`_stronger`:
`eq` over `ule`, `ult` over `ule` and `ne`, ...); `a != 0` proves `0 <u a`;
equality and disequality hold at any offset, as a wrapping sum is a
bijection. `implies_at_offset` does the signed case where the sides differ
only in constants (`n > 2` proves `1 < n - 1`), exact only where the caller
knows nothing wraps.

`holds(unit, at, predicate, left, right)` is true when both sides are
constants and the compare is true (`evaluated`), when a guard implies it,
when it is an unsigned compare of zero extensions that a guard proves in the
narrow type (`narrowed`), or when it is a compare of a phi against a value
fixed over the loop, where each incoming edge proves it of the value it
brings (`through_phi`: a loop entered from a guard and from its own latch
test). `holds_given` and `Given` add the `assumed` guards a caller supplies,
the guards on each loop's followers of its counters (`start <= follower <=
counter`) and the program's stated ranges, and ask
`crate::difference::proves`; `Given` finds the guards of a block once for
as many questions as are asked of it.

### Provides
Guard facts and the implication queries above. Consumers: `decide`,
`exitfold` and `jumpthread` in `llrm-transforms`, and
`crate::induction` (loop entry guards).

### Needs
`crate::cfg::Shape`, `crate::assumptions`, `crate::induction`'s `Scev`
(`term`, `followers_of`), `crate::ranges::declared` and
`crate::difference`.

### See also
LLVM `isBasicBlockEntryGuardedByCond`, as far as direct implication goes;
`ScalarEvolution::collectFromBlock`, which climbs the unique-predecessor
chain only
([`ScalarEvolution.cpp:16199`](https://github.com/llvm/llvm-project/blob/d1106deb71cc81016406a1917d0508d2df296266/llvm/lib/Analysis/ScalarEvolution.cpp#L16199)).

## induction

Source: [`crates/opt/llrm-analysis/src/induction.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/induction.rs)

Which values are affine functions of a loop's counter, and how many trips a
loop makes.

### How it works
Three layers, each built on the one before.

Counters. `basics(unit, loop)` finds the header phis that one invariant or
constant step (`add`, or `sub` of a constant) advances on every way round,
from one start on every way in: an `Affine { value, start, step, header }`,
`start + step * trip`. `pointers` finds pointer phis stepped by constant
bytes through a `getelementptr`. `followers` finds header phis that advance
by at most one a trip wherever a counter advances by one without wrapping.

Trip counts. `counted(unit, loop, ..)` returns a `CountedLoop` proof for a
loop with one latch and one conditional exit that goes on (`_control`: the
branch is in the header or the latch, a latch that only jumps back being the
end of its predecessor). The proof says the counter, its start and bound,
the `IntPredicate` that continues the loop, whether it is tested before or
after the trip (`posttested`) and on the stepped value (`stepped`), and how
the count is reached (`Reach`):

- `Distance`: `bound - start`, one more if the test is inclusive.
- `Solved`: where `start + k * step == bound` modulo the width, as LLVM's
  `howFarToZero`.
- `Ceil`: an ordered test with a step above one that is promised not to
  wrap, the distance divided by the step, rounded up (`howManyLessThans`).

`count` is the exact count when constant, `maximum` bounds an unknown one,
and `first` and `last` are the counter's signed values on the first and last
trip, given only when nothing wraps. A symbolic count is built on demand by
`trips` (and `exit_value`), which asks the caller to place each preheader
operation. `counted_unless_stopped` also accepts a loop that leaves into a
block that never returns (`stops`, using `crate::noreturn::stranded`);
`counted_leaving` also other exits that go on. `exits` counts every exit of
a single-latch loop, as LLVM's exit limits. The manager keeps `counted_all`
as the `Counted` analysis, and a unit that carries it is read without a
re-proof.

Recurrences. A `Scev` is a polynomial in loop-invariant unknowns modulo a
width (sums of `Monomial`s, at most 16 terms and degree 4), in one canonical
form so equal values are equal. A `Recurrence` is `pointer + start + step *
trip` with `Scev` start and step: LLVM's add recurrence. `recurrences` walks
a loop and gives every value affine in a counter one; `users` lists the
operands that read them, each as an `IvUse` of kind `Address`, `Compare` or
`Basic` with the low bits it observes (LLVM's IVUsers).

```text
  pre:    ...
  header: %i = phi [0, pre], [%n, latch]     Affine{start 0, step 1}
          %c = icmp slt %i, %len             test: Slt, bound %len
          br %c, body, exit                  Reach::Distance
  body:   %p = gep %a, %i                    Recurrence{pointer %a, step 4}
  latch:  %n = add %i, 1                     trips = %len - 0
```

Proofs of removal are `control_replacement` (the counter's phi is read only
by its compare, its step and the exit's phis, so the loop's own control may
go) and `zero_terminating_control` (a counter reaching its final value ends
control and takes no value twice in the trip count).

### Provides
`AffineOperand`, `Affine`, `CountedLoop`, `Counted`, `ExitCount`, `Scev`,
`Recurrence`, `Users`, `LoopFollowers` and the functions above. Manager
entries: `Counted` (incremental) and `Followers`. Consumers:
`crate::ranges`, `crate::alias`, `crate::peelsize`,
`crate::difference`, `crate::guards`, `crate::floatfacts`, and in
llrm-transforms `indvars`, `lsr`, `loopexit`, `peel`, `unroll`,
`unroll_jam`, `rotate`, `decide`, `hoist`, `expand`, `exitfold`, `counting`,
`window`, `fill`, `floatloop`.

### Needs
`crate::consts` (the registers the proofs read), `crate::occurrence`,
`crate::noreturn`, `crate::cfg` (loops, dominance).

### See also
LLVM ScalarEvolution add recurrences and trip counts, InductionDescriptor,
IVUsers.

## interprocedural

Source: [`crates/opt/llrm-analysis/src/interprocedural.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/interprocedural.rs)

Facts that cross direct procedure boundaries: constant arguments, constant
returns, purity and termination of calls.

### How it works
A direct call is opaque to ordinary SCCP even when every return of the named
body has the same value. These functions compute that over a module (or,
with `program_*`, a whole program) and write it into the body, where the
ordinary pipeline folds the consumers.

Arguments. `current_call_constants` lists, per call or `invoke` with a known
callee, the integer-constant actuals. `constant_parameters` (and
`program_parameters`, which also reads other modules' calls) keeps, for each
`eligible` (private) body, the parameter positions where every call agrees
on one constant; a recursive call that passes the parameter on at the same
position adds no new value. `specialize_parameters` replaces the uses of
such a parameter by the constant.

Returns. `constant_returns` finds, for each exactly defined body, the one
integer every `ret` returns. `propagate_returns` replaces uses of a direct
call's result by it; the call stays, and only a separate purity proof erases
it.

```text
 caller:  %r = call @g(i32 5)        g(%x): ... ret i32 7
                                     (every call passes 5, every ret 7)
 after:   %r = call @g(i32 5)        g(%x): uses of %x become 5
          uses of %r become 7
```

Purity and termination, as stated by attributes the whole-module step
stamped on each body. `stated_pure` is the exactly defined bodies that state
no memory effect, `willreturn` and `nounwind`. `erasable` asks the same of
one call (LLVM's `wouldInstructionBeTriviallyDead`), and
`remove_dead_pure_calls` erases the calls with no used result that are
erasable. `returns_without_looping` holds when every CFG path ends in `ret`
without revisiting a block. `cannot_fault` holds when every access is
non-volatile and either in a frame object (`frameescape::framed`) or a
constant offset (`crate::pointerfacts`) from an initialized near global
this module defines.

Noreturn. `noreturn_procedures` and `program_noreturn` are
`crate::noreturn`'s greatest fixed point over the eligible bodies;
`terminal_calls` applies its cut after the calls to them.

A body is exactly defined when its linkage says the definition here is the
one that runs (LLVM's `hasExactDefinition`).

The functions above, and the re-export of `noreturn::terminal_sites`.
Consumers: the `interprocedural` program pass and `ipacp` in
llrm-transforms.

`crate::effects` (`callee`, `states`, `writes_memory`), `crate::cfg`,

LLVM's IPSCCP.

## liveness

Source: [`crates/opt/llrm-analysis/src/liveness.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/liveness.rs)

Which SSA values are live at each block's entry and exit, and how many are
live at once.

### How it works
`live` returns `Liveness { live_in, live_out }`, keyed by `cfg::id`. It is
the least solution of

```text
 out(B)   = union of in(S) over successors S, plus the arms of S's live
            phis that come from B
 after(B) = out(B) - defs(B) + exposed(B)   (exposed: read before written)
 in(B)    = after(B) - phis(B)
```

Rather than iterate bit sets over every value, `solved` follows each value
from where it is read back to where it is made: a worklist of `Out(block,
value)` and `After(block, value)` facts. A value reaching its defining
block's ordinary operations stops there; one reaching its defining phi
continues along each predecessor edge with that edge's arm. The work is the
size of the live sets, not blocks times values. gcc's
`calculate_live_on_exit` and LLVM's `LiveVariables` walk from each use too.
A phi's arm is live out of the predecessor it comes from, not in the phi's
block.

```text
   B0:  %a = ...                 %a live_out(B0), live_in(B1) (read in B1)
   B1:  %p = phi [%a, B0], [%b, B2]    arm %a is live_out(B0) only
        ...                      %b live_out(B2)
   B2:  %b = ...
```

`live_where` solves for a chosen set of values only, plus the phis that take
them as arms, so a caller asking about a few values (the phis a pass takes
for cells) does not pay for the whole function. `entry_values` are the
values used and defined nowhere in the body: the parameters.

Pressure. `pressure` is the most values live at once, over the function or
over the blocks `inside`; `pressure_of` counts only values a predicate
accepts. It starts from `live_out` and walks each block backward.
Per-instruction views: `live_points` (live before and across each
instruction), `each_across` (the same over one set updated as it goes,
avoiding a copy per instruction), `live_steps` (the changes between
neighbouring instructions) and `pressure_points`. `phi_inputs` gives the
edge operands of phis whose results are live. `solves` counts the solves on
this thread, so a test can check that a caller reuses the one it holds.

Under `cfg(test)`, `live` is checked against a bit-set fixed point
(`live_dense`) on every function a test gives it.

### Provides
`Liveness`, `live`, `live_where`, `pressure`, `pressure_of`, `entry_values`,
`live_points`, `each_across`, `live_steps`, `pressure_points`, `phi_inputs`.
Consumers in llrm-transforms: `homes`, `spill`, `lsr`, `indvars`, `inline`.
The machine phases use `backend/liveness.rs`, over physical register lanes.

### See also
GCC `calculate_live_on_exit` (`tree-ssa-live.cc`); LLVM `LiveVariables`.

## manager

Source: [`crates/opt/llrm-analysis/src/manager.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/manager.rs)

The memory and range analyses as entries of llrm-mir's analysis manager:
asked for by name, cached, kept or brought up to date after a pass.

### How it works
A pass asks `analyses.get::<A>(context, layout, function)` and receives a
shared result. The manager computes it once, hands the same `Rc` to every
later asker, and decides after each pass what to do with it. The entries
here declare how, through the `Analysis` trait of `llrm_mir::passes`:

- A pass returns the `PreservedAnalyses` it left true. An entry not named is
  dropped, unless `READS_OUTER` is false (it reads only the function, as
  `DemandedBits` and `Shape`) and the function is unchanged.
- `SKIPS` with `depends`: the entry is kept past an invalidation if the
  change log cannot have altered it. `Depends` names the instructions the
  result models, those it keys entries by, and the users a change flows
  through. `ExposedFrames`, `PointerValues`, `Pointers`, `CallEffects` and
  `Writes` model pointers, aggregates and calls only, so a change to integer
  arithmetic leaves them standing.
- `INCREMENTAL` with `update`: the entry is brought up to date from the
  change log. `DominatedEdges`, `Bounded` and `Counted` redo only the blocks
  or loops `reached_by` the changes (a change to a terminator or to the CFG
  redoes all); `Accesses` in `crate::memoryssa` survives pure moves.
- `LLRM_CHECK_REPLAY` asserts that every kept or updated result equals a
  fresh `run`.

```text
 pass runs ---> PreservedAnalyses
                  |
   entry named? --yes--> kept
        |no
   READS_OUTER=false and function unchanged? --yes--> kept
        |no
   SKIPS and depends.unaffected(changes)? ------yes--> kept, stands again
        |no                                              if changes undone
   INCREMENTAL and update(previous, changes)? --Some--> updated
        |no
   dropped; recomputed on the next get
```

Function entries and what each asks for (every one also asks `Shape`, and
most `AssumptionCache` and `ExposedFrames`, which are omitted):

```text
 PointerValues    -
 Pointers         PointerValues
 CallEffects      PointerValues
 Writes           CallEffects
 Registers        -
 Followers        Registers
 Counted          Registers
 DominatedEdges   Registers
 Bounded          Registers, Counted, DominatedEdges
 Annotated        Pointers, Registers, Counted, DominatedEdges, Bounded
 Accesses         Annotated, CallEffects                  (memoryssa)
 ThroughMemory    Writes, Annotated, Registers
 FloatFacts       ThroughMemory, Writes, Annotated, Registers
 Published        Pointers, ExposedFrames                 (observers)
```

Module entries read the program through `ModuleAnalyses` and are dropped
unless every run of a pass preserved them. `GlobalsAA` (which globals no
outside code reaches but by name) and `Summaries` (each defined function's
memory effects, by name) can be held past passes that add no memory
operation when `covers` says the stale result states no more than a fresh
one. `Summaries` keeps per-body facts and recomputes only bodies whose
history moved. `Callbacks`, the effects of all the callbacks into the module
added up, is rebuilt only when `GlobalsAA` or `Summaries` is a different
result. `ProgramSummaries` is a program entry: one fixed point over all
modules, each module's `Summaries` given the others'.

`Unit::within` builds the `Unit` that analyses read from `Outer` (the
module, target and program), carrying whichever cached results the caller
holds. `Held` and `Ranges` bundle the cached results a pass passes on to a
`Unit`, so the facts are the manager's and not a solve of the pass's own.
`Bounded` is empty where `Outer::loop_intervals` is off (-O1).

### Provides
The entries: `ExposedFrames`, `PointerValues`, `Pointers`, `Annotated`,
`CallEffects`, `Writes`, `Registers`, `DemandedBits`, `AssumptionCache`,
`Followers`, `Counted`, `ThroughMemory`, `FloatFacts`, `DominatedEdges`,
`Bounded`; module entries `GlobalsAA`, `Summaries`, `Callbacks`; program
entry `ProgramSummaries`; `Held`, `Ranges`, `reached_by`, `call_effects`,
`writes`. `crate::cfg`'s `Shape`, `crate::memoryssa`'s `Accesses`,
`crate::observers`'s `Published` and `crate::noreturn`'s `TerminalSites`

`crate::alias`, `crate::consts`, `crate::globalsaa`,
`crate::induction`, `crate::ranges`, `crate::floatfacts`,
`crate::frameescape`.

is in `crates/ir/llrm-mir/src/passes.rs`.

## memory

Source: [`crates/opt/llrm-analysis/src/memory.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/memory.rs)

The memory model every alias query reads: objects, byte slices, provenance,
accesses (`MemRef`) and the `Unit` that carries a function's facts.

### How it works
An object is what LLVM calls an underlying object (`MemoryObject`, interned
per module as `ObjectRef`). Its `MemoryKind` is one of:

- `Frame`: an `alloca`.
- `Global`: a global variable.
- `Parameter`: what a pointer parameter points to.
- `Unknown`: a pointer no fact follows.
- `Nonlocal`: what a callee may reach.
- `Absolute`: linear memory (`regions::linear`).
- `Stack`, `External`, `Named`, `Allocation`: kept for `classes_may_alias`;
  the rich MIR has no producer for them (an allocation is the `!tbaa` type
  "allocation" on the access).

Besides its identity an object carries three facts that equality ignores:
`addressed` (some code computes its address), `captured` (that address can
be found from outside this activation) and `constant` (nothing writes it).
`objects_may_alias` asks only the `AliasClass` (kind, addressed, captured):

```text
  an unaddressed object            -> reached only by its own name
  Unknown vs x                     -> x.captured
  Nonlocal vs x                    -> x.captured and x is not Frame/Stack
  Parameter vs x                   -> x.captured and x is not Frame
  Global/External vs Global/External -> only if one is External
  anything else (distinct)         -> no
```

A `Slice` is bytes of one object: `[low, high)` with `stride` and `width`,
so a stride above one selects byte lanes, not their hull. `WHOLE_LOW..
WHOLE_HIGH` is "any byte". `Slice::intersects` is exact for one object (gcd
of the strides) and, for two distinct objects that may alias, true. A
`Provenance` is a set of slices plus the `restrict` roots (`noalias`
parameters) a pointer is based on; two with disjoint nonempty restrict sets
do not intersect.

`MemRef` is an access, LLVM's `MemoryLocation`, with its pointer decomposed
as BasicAA's `DecomposeGEPExpression` does: a `root`, a constant `disp`
wrapped to the index width, and at most one variable index (`base`,
`scale`), plus the width, `!tbaa` type and its ancestors (`lineage`), and
`volatile`. `MemRef::of` builds it from a load or store, `filled` from a
constant-length `memset`, `reach` from provenance alone (what a call's
effect names). `named` says the bytes are fixed outright; `unwritable` that
every object it may reach is `constant`.

`Unit` is what the analyses read: the function, its module's types,
constants, layout, metadata and globals, the program's target and segment
layout, and optional facts handed in with `with_*` (shape, registers,
pointers, annotated references, assumptions, counted loops, bounds, edges,
exposed frames, GlobalsAA, callbacks). A fact not handed in is derived on
demand, which is correct but repeats work; `crate::manager`'s
`Unit::within` fills them from cached analyses. `Standing` holds the
registers for a caller that edits the body as it goes. `constant_bits` and
`constant_bytes` read a `constant` global's initializer. `own_bytes` is the
one statement of what a load or store does to its bytes, and
`unmodeled_write` says whether any other instruction may write.

### Provides
The types above; `exposed_frames`, `object_of`, `global_object`, `typed`,
`lineage`, `is_lifetime_marker`. Consumers: nearly every analysis in this
crate (`crate::alias`, `crate::memoryssa`, `crate::regions`,
`crate::avail`, `crate::consts`, `crate::effects`) and the memory
passes of llrm-transforms.

### See also
LLVM BasicAA `DecomposeGEPExpression` and `MemoryLocation`
(`llvm/lib/Analysis/BasicAliasAnalysis.cpp`).

## memoryssa

Source: [`crates/opt/llrm-analysis/src/memoryssa.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/memoryssa.rs)

Memory SSA: a single memory state versioned by stores and writing calls,
with a walker that finds the writes a load may see.

### How it works
`Accesses` records what each instruction touches: a load's or store's own
`MemRef`, a call's footprint (its `CallEffects`, or anything its attributes
allow), and the bytes a call fills before reading any. It is the manager's
`accesses` analysis, built from `crate::manager`'s `Annotated` and
`CallEffects`, and kept across changes that only move instructions or give a
store another value (`update`).

`built` numbers the accesses. Every instruction that writes (`None` writes
means anything) is a `Def`; one that only reads memory is a `Use`; one that
touches none is skipped. Each access names the access before it in its block
as `defining`. Each block starts in a memory `Phi` over its predecessors'
exit states, with the entry block also fed by `Live`, the state on entry to
the function. Phis are wired before they are resolved, so back edges need no
iteration over memory versions; then phis whose inputs reduce to one state
are replaced by it.

```text
        entry: Live(0)
          |
   b1: Def s1 --(defining)--> Def s2 ---+
          |                              |
   b2: Phi [b1: s2, b3: s3]  <-----------+----- b3: Def s3
          |
         Use l1   (defining = Phi)
```

The walker (`clobbers`, `clobbers_at_end`, `nearest_writes`) answers, for a
`MemRef` read at a site, the set of nearest defs whose write may change it,
or `Live`. It steps up `defining` links and through every phi input,
skipping defs that `may_clobber` rules out: a constant or `invariant` read
is changed by nothing; two references at fixed displacements of one frame
whose bytes miss are settled by `regions::displaced_span`; otherwise
`crate::pointerfacts` disjointness is tried before `regions::overlapping`.
Per (cell, def) answers are remembered, and a walk jumps along chains of
accesses that leave the cell alone. After enough steps per access, a
persistent map from (object, byte) to the nearest def writing it replaces
stepping. A visited set closes cycles without taking a back edge as evidence
that memory is unchanged. An empty answer means no reachable source, not a
reusable value; the caller must establish value availability itself.
`nearest_writes` stops after `MAX_NEAREST_WRITES` (100) and the caller
serves nothing past that. `unchanged` and `available_on_edge` answer whether
an earlier access still supplies the bytes, the caller having proved
dominance and equal addresses.

Predicates shared with the passes: `changes`, `spares`, `covers`/`covered`
(outer references certainly hold every byte of the inner), `placed`,
`same_bytes`, `byte_keys`, and `Writers`, which indexes writes by object.

## nearest

Source: [`crates/opt/llrm-analysis/src/nearest.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/nearest.rs)

The items placed in blocks that dominate a given block, nearest first.

### How it works
Loads look for a provider among the stores and loads that dominate them.
Scanning every item of the function per load is quadratic. `Nearest::of`
builds, per key, the blocks that hold an item of that key, sorted by their
preorder number in the dominator tree, and links each to the nearest block
above it in the tree that also holds one. `Nearest::dominating` binary
searches for the last block at or before the query block, walks the links up
until a block's subtree span contains the query, and yields the items from
there up. The work is the length of that chain, not of the function.

```text
 dominator tree           key K holds items in A, C, E
      entry                 sorted by preorder: A  C  E
       |                    up links:           -  A  C
       A (K)                query at F (under E): last block <= F is E
      / \                   chain E -> C -> A
     B   C (K)
         |
         E (K)
         |
         F  <- query
```

Items of several keys are merged by a cursor per key: the walk takes the
largest preorder number first, and within a block the last item first. An
item reached through two keys is returned once. A block the dominator tree
does not reach is left out of the chains and, as the query, yields nothing:
everything dominates it, so the caller decides.

### Provides
The `Nearest` index and its `Walk` iterator. Consumers: `crate::avail` and
`loadjoins` in llrm-transforms.

### Needs
`llrm_mir::dominators::DominatorTree` (`span`, the preorder interval of a
block).

## noreturn

Source: [`crates/opt/llrm-analysis/src/noreturn.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/noreturn.rs)

Which bodies and blocks cannot reach a normal return, and the edit that cuts
a block after a call that cannot return.

### How it works
A call is terminal when its callee is in the given `noreturn` set or the
call or callee states `noreturn` (`terminal_sites`; an `invoke` may still
unwind, so only a `call` counts). `_cannot_return` walks the CFG from the
entry, stopping at a block holding a terminal call; if it reaches a block
ending in `ret`, the body can return.

`inferred` and `inferred_in` (over a program, so a declaration of a proven
body stops as the body does) find the greatest set of bodies none of which
returns. Every body starts in the set; a body that can return, given the
calls to bodies still in the set, leaves it, and only its callers are looked
at again, as gcc's ipa-pure-const propagates. Starting full lets a closed
recursive SCC prove terminal.

`cold` finds blocks from which every path ends in a terminal call, an
`unreachable`, or a block with a call that states `cold`. It is a least
fixed point, so a loop that never exits is not cold, and when the entry is
cold the result is empty. `stranded(function, header)` finds blocks from
which no path reaches a `ret` or the header: a loop that exits into one
stops the program.

`after_terminal_calls` is the edit. In each block, everything after the
first terminal call is erased (uses replaced by `poison`), the call is kept
as the observable action, and the block ends in `unreachable`.
`cfg::_unreachable` then removes blocks the entry no longer reaches.

```text
   bb:                         bb:
     %a = call @exit(1)          %a = call @exit(1)   ; kept
     %b = add %a, 1      -->     unreachable
     store %b, %p
     br %next                  %next loses bb as a predecessor
```

### Provides
`TerminalSites` (analysis of the function with no body proven noreturn),
`terminal_sites`, `inferred`, `inferred_in`, `cold`, `stranded`,
`after_terminal_calls`. Consumers: `crate::interprocedural`
(`noreturn_procedures`, `terminal_calls`), `crate::branchprob` (`cold`),
`crate::induction` (`stranded`) and the `hoist` pass in llrm-transforms.

### Needs
`crate::effects` (`callee`, `states` for the `noreturn` and `cold`
attributes), `crate::cfg`.

## observers

Source: [`crates/opt/llrm-analysis/src/observers.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/observers.rs)

Which memory cells nothing outside a function can read.

### How it works
A store is dead when everything after it overwrites the cell before reading
it, or when nothing after it can read the cell at all. `avail::dead_stores`
answers the first; this answers the second: at a call or an exit, which
cells are still observable.

`private` returns a test on a `MemRef`. A reference is private when its
provenance is non-empty and every slice lies inside a `Frame` object, within
that object's extent, whose address did not escape (`PointsTo::escaped`: a
call, a return, a `ptrtoint` or a store outside the frame) and that is not
published. Globals are never private: other functions and, unless
`internal`, other modules reach them.

An object is published when something reads it without naming it:

1. A load or store whose `MemRef` is not `named` (a variable index into a
   local is not a name) publishes every known object in its provenance.
2. A call publishes the objects of its read arguments. `nocapture` keeps the
   address from escaping, not the callee from reading it during the call.
3. A pointer stored into a published object publishes its pointee, repeated
   to a fixed point: a callee given a struct loads the pointer in it.

```text
 %s = alloca {ptr}      store %buf -> %s      call @f(ptr %s)
                                                  |
   %s  published (read argument) ----------------+
   %buf published (stored into %s, step 3)
```

### Provides
`private` and `private_of` (the same test with `Published`, the manager's
cached set, passed in), and the `Published` analysis. Consumer: the `dse`
pass in llrm-transforms.

`crate::manager`'s `Pointers` (points-to) and `ExposedFrames`,
`crate::alias`, `crate::memory`.

## parameter_ranges

Source: [`crates/opt/llrm-analysis/src/parameter_ranges.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/parameter_ranges.rs)

The range of each integer parameter of a body only the program calls, from
what its callers pass.

### How it works
`stamp` takes the bodies that are neither exported nor address-taken. For
each integer parameter that has users and no `range` attribute, it collects
what every direct call (`call` or `invoke`) passes. A call's actual is read
in its caller by `crate::ranges` under the interval scope of the call's
block, with the caller's own parameters' stamps, and for an operand with no
interval, computed from its operands two levels down. A call in a block
`ranges` finds unreachable passes nothing. The actuals are joined into
`Seen`: `Nothing`, `Within(interval)` or `Anything`. A caller that has not
itself been seen yet is `waiting` and does not turn an unknown actual into
`Anything`.

Rounds repeat, each stamping what the last round saw as a `range` attribute
on the callee, so the next round's callers read it. A recursion that passes
`row + 1` under `row != 7` is found this way.

```text
 f(row) called with 0, and by f itself as f(row + 1) under row != 7
 round 0   callers outside pass 0            row in [0,0]
 round 1   f(row + 1) under row != 7         row in [0,1]
 round 2   still growing: high jumps to the next number f compares row
           with (6, 7 or 8)                  row in [0,6]
 round 3   6 + 1 is 7: high jumps to 7       row in [0,7]
 round 4   no change: fixed point, stamps stay
```

From the third round (`round >= 2`) a bound that still moves jumps to the
next number the callee compares the parameter with (one either side of each
`icmp` constant, then the type's bounds). After `ROUNDS` (8) with no fixed
point every stamp of the call is withdrawn and nothing is returned: a stamp
is a promise, and only a fixed point keeps it. A parameter seen to be
`Anything` loses an earlier stamp. A range covering the whole type states
nothing and is not stamped.

### Provides
`stamp`: a `range` attribute on each integer parameter whose callers all
pass a known range, and the set of bodies stamped. Consumer: the
`interprocedural` program pass in llrm-transforms, which calls it up to 4
times after its constant and inlining rounds when `Interprocedural::ranges`
is set (gcc's `-fipa-vrp`, -O2 and up), re-optimises the bodies it returns
and stops when none.

### Needs
`crate::ranges` (`bounds`, interval of an operand), `crate::consts`,
`crate::effects` for `callee`, `llrm_mir::program::Program`.

### See also
LLVM's IPSCCP, which states an argument's range as a `range` attribute where
it has no single constant.

## peelsize

Source: [`crates/opt/llrm-analysis/src/peelsize.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/peelsize.rs)

Whether a loop is worth copying out completely, decided before anything is
cloned.

### How it works
`admitted(unit, loop, count, facts, limits, site)` answers for a loop whose
trip `count` is known. The decision is GCC's `try_unroll_loop_completely`;
the size it is given is LLVM's `analyzeLoopUnrollCost`. Budgets count MIR
instructions, as GCC's `--param`s count insns, so no machine number enters.

Size. `unrolled` runs each of the `count` iterations over the values it
knows (the header phis take the previous iteration's values) and the memory
it has written. An instruction that folds (`consts`) costs nothing; one that
does not adds its size (1, or its operand count for a call lowered to one).
A branch or `switch` on a known value follows only the chosen successor; an
undecided one adds 1 to the size and to `branches`. It gives up once the
size passes the budget. It also sums `rolled`, the instructions the rolled
loop would execute over all iterations.

```text
  rolled loop (count = 3)           copied out
  header: i = phi [0, i+1]          i = 0   (folds)
          t = i * 4   (folds)       t = 0   (folds)
          x = load p[t]             x0 = load p[0]    cost 1
          br i < 3                  (decided: no branch kept)
  size = unfolded ops over 3 iterations; rolled = all ops over 3
```

The tests, in order:

1. The language's `unroll` hint on a latch: 0 refuses; fewer permitted
   copies than `count` refuses (no partial unrolling); otherwise the copy is
   asked for and is judged against `HINTED_OPERATIONS` (16384).
2. Unhinted, more than `max_unroll_iterations` (16; 0 is unbounded) refuses.
3. A loop holding another loop (`_ordered` fails) is copied only when that
   shrinks it: `count * (size - folded) <= size`.
4. The simulated copy's size is scaled by two thirds, for what later passes
   remove. A copy no larger than the loop, or one asked for, is admitted.
   Otherwise it is refused when `grows` is false (-Os), when the loop is
   cold (`Site::entries` under 5% of an entry), when it holds a call that
   touches memory (`Site::writes`), when undecided branches exceed 32
   (`max-peel-branches`), or when the scaled size exceeds
   `max_unrolled_operations` times the boost. The boost is LLVM's
   `getFullUnrollBoostingFactor`: `rolled / size` in percent, capped at 400.

`Limits::on` replaces `max_unrolled_operations` by `target_percent` of the
target's `unroll_budget` where both are set. Each decision is logged under
the `unroll` debug tag.

### Provides
`admitted`, `Limits`, `Site`. Consumers: the `peel` and `unroll` passes in
llrm-transforms (`profit` builds the `Site`).

### Needs
`crate::consts` (folding of an instruction over known values),
`crate::induction` (`basics`, the loop's counters), `crate::cfg`,
`crate::graph` loops.

### See also
GCC `try_unroll_loop_completely`, `estimated_unrolled_size`
(`gcc/tree-ssa-loop-ivcanon.cc`); LLVM `analyzeLoopUnrollCost` and
`shouldFullUnroll` in `LoopUnrollPass`.

## pointerfacts

Constant byte offsets between pointer values, and disjointness of two

### How it works

then does `comparable` return their two offsets, and `disjoint` and

`Location`s. Two unrelated pointer values never prove disjointness.

            |
            +--- gep inbounds 8  -> %b   (relative: (%base, 8))
  Location{%a, 8} and Location{%b, 4} are disjoint: 0 + 8 <= 8

## ranges

Source: [`crates/opt/llrm-analysis/src/ranges.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/ranges.rs)

Non-wrapping integer intervals per block, from the branch edges that
dominate a block and the counted loops that hold it.

### How it works
An `Interval` is `[low, high]` over mathematical integers at a bit width,
signed. A value's interval is the intersection of what several sources give.

Operands. `_operand` reads a constant's, an entry in the scope's
`Intervals`, a parameter's `range` attribute or a `!range` on a load or call
(`declared`), or a single known value from `crate::consts`. `_computed`
gives what an instruction computes from its operands' intervals (`add`,
`sub`, `mul`, `shl`, `and`, `sext`, `zext`, fixed-point multiply), and no
interval where the result could wrap.

Edges. `dominated_edges` walks the dominator tree. A conditional `br` on an
`icmp` narrows the compared values on each edge (`on_edge`): signed
predicates move bounds, `eq` intersects, `ne` trims an end when the other
side is a point, unsigned ones only decide whether the edge is possible, and
`assume` calls add facts. `_refine_through` pushes a bound back through the
`add` or `sub` that made the value. An edge counts only when its destination
has that one predecessor, because a join is another way around the check; a
block starts from its sole predecessor's facts narrowed by the edge, or else
its immediate dominator's. An edge no execution takes makes the block
unreachable. `EdgeStates` keeps each block's state so a change re-solves
only the blocks it reaches (`edges_solved`).

Loops. `bounded_solved` handles each counted loop (`induction`'s trip
counts) outer first. A counter that steps by a constant from a known start
gets the interval its trip count allows (`_recurrence_span` refuses
wrapping), a header that tests before the trip also sees the exit value, and
a counter with an `nsw` step never goes back past its start. The loop's
operations are then swept to a fixed point in the scope of each block,
narrowed by the edges inside the loop and above its header. Header phis with
no counted proof that stay inside a box `[-2^k, 2^k)` on every entry and
latch are given the box, grown by powers of two until the latches stay in
it. Two loops whose facts contradict at a block make it `unreachable`.
`Bounds` holds the result: facts from the loops (`within`) over those from
the edges. A change re-solves only the loops it reaches (`loops_reached`).

```text
  entry:  ...
  b1:     %c = icmp slt %i, 10         b2 (taken):    %i in [lo, 9]
          br %c, b2, b3                b3 (not taken): %i in [10, hi]
  loop:   %i = phi [0, pre], [%n, latch]; %n = add nsw %i, 1
          counted trips 10    ->  %i in [0, 9] in the body, [0, 10] at exit
```

Queries. `scoped` is every block's intervals (loops narrowed by edges);
`operand_at` is one operand's at one block without copying the rest.
`covering` widens an indexed access into its own object to the byte interval
it can touch; `inside_object` says that interval lies inside the object.
`exact_offsets` finds index values whose every access sums, at any wider
width, to the same bytes, because every partial sum is a non-negative
integer below `2**index_bits`; it is used where the object's own address is
the only root known to start at 0.

### Provides
The interval facts above. In the manager they are `DominatedEdges` and
`Bounded` (both incremental) and `Ranges`, which bundles them with registers
for a pass; `Bounded` is held only when `Outer::loop_intervals` is on (-O2
and up). Consumers: `crate::alias`, `crate::regions`, `crate::guards`,
`crate::memoryssa`, `crate::avail`, `crate::parameter_ranges`, and in
llrm-transforms `algebraic`, `hoist`, `loopexit`, `indvars`, `decide`,
`fixednarrow`, `ports`, `interprocedural`.

### Needs
`crate::consts` (`Known`, the registers), `crate::induction` (counted
loops), `crate::assumptions`, `crate::cfg` (shape and dominance).

### See also
GCC's ranger (`gimple-range-cache.cc`, `ranger_cache::range_on_entry`);
LLVM's LazyValueInfo and ScalarEvolution value ranges.

## regions

Source: [`crates/opt/llrm-analysis/src/regions.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/regions.rs)

Whether two memory references can meet: `may_alias`, `overlapping`, and the
indexes that find the candidates without comparing every pair.

### How it works
`overlapping(one, other, known, other_known, program)` asks whether a write
through `other` could land on `one`, in this order:

1. `typed_apart`: accesses of different `!tbaa` types of one root, neither
   type an ancestor of the other, cannot alias, unless the address analysis
   already has them at overlapping bytes (`provably_overlap`) or at one
   start (`same_typed_start`). It is asked as LLVM's TypeBasedAA is, only to
   separate what addresses cannot.
2. `foreign_apart`: one reference is in an address space that holds program
   data and the other, by its selector's range, lands wholly in linear
   memory the target keeps no program data in (`foreign`).
3. Both with provenance: `_displaced` (two references off one root and one
   scaled index are disjoint by displacement, LLVM's constant-offset GEP
   compare) if they share a frame, else `may_alias`.
4. Otherwise a reference that only a named object reaches (`_unescaped`) is
   not reached by one through a pointer value. With range facts, an indexed
   reference is first widened to the hull of its range (`ranges::covering`),
   then `_displaced` again, then `may_alias`.

`may_alias` refines each reference to the bytes it may name under its own
interval facts, `foreign` linear bytes or its provenance `narrowed`: an
indexed access into its own object with a range fact on the index names
`[disp + scale * low, disp + scale * high]` plus the access width, when that
lies inside the object's extent. Refining that cannot be expressed in
`Slice` endpoints is a `RegionError`, and the caller treats it as overlap.
The two refined provenances then decide by `Provenance::intersects`. A
reference with no provenance is not proven apart from anything.

```text
   A: p + 4 (width 4)     B: p + 8 (width 4)     one frame (p, no index)
   A = [4, 8), B = [8, 12)  ->  _displaced: disjoint, no object reasoning
```

Finding candidates. A `CellMap` indexes cells by `OverlapBucket`: an
interned (object, frame, alias class) shape. `overlap_buckets` picks, for a
write, only the buckets that can hold a cell `overlapping` does not rule
out: objectless ones, the write's frame, its objects, and any class that may
alias. `displaced_buckets` and `displaced_span` serve a write at fixed
displacements in a frame. `Index` does the same for lists of references:
`near` returns the entries that name an object the reference may alias,
every addressed one if the reference names an addressed object, and every
entry without provenance; more than needed, never fewer.

Which linear memory holds no program data is the target's fact, and which
address spaces hold program data the segment layout's; both come from the
program the manager hands analyses as `Outer::program`.

### Provides
`may_alias`, `overlapping`, `typed_apart`, `foreign_provenance`,
`fixed_provenance`, the bucket functions, `displaced_span`, `Index`.
Consumers: `crate::alias`, `crate::memoryssa`, `crate::avail`,
`crate::consts`, `crate::floatfacts`, `crate::cellmap`, and in
llrm-transforms `promote`, `transform`, `homes`, `loopmotion`, `fill`,
`floatloop`.

### Needs
`crate::memory` (`MemRef`, `Provenance`, alias classes) and
`crate::ranges` (`Interval`, `covering`).

### See also
LLVM BasicAA's constant-offset GEP comparison and TypeBasedAA.

## sliceset

Source: [`crates/opt/llrm-analysis/src/sliceset.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/sliceset.rs)

An ordered set of memory slices that holds most of itself as a run shared
with other sets.

### How it works
A function that may call back into the module (an address-taken function or
an entry) has, in its summary, the effects of all those callbacks. That run
of slices is the same for every such summary, every instantiation of it at a
call and every call's effect. Building, comparing, filtering and listing a
tree set holding it each time is wasted work.

`Shared` is one immutable run of slices behind an `Rc`, with facts computed
once: whether none is in a `Frame` or `Stack` object (`outlives`), whether
any is a `Parameter`'s, and which objects it holds whole or in part. A
`SliceSet` is `own` (a `BTreeSet<Slice>`) plus an optional `base:
Rc<Shared>`, the two disjoint. Seen as a set, it is exactly the union.

```text
 SliceSet                    Shared (one allocation, many holders)
 +------+---------+          +---------------------------------+
 | own  | base ---+--------> | set, outlives, parameters,      |
 | few  |         |          | wholes, parts, coalesced        |
 +------+---------+          +---------------------------------+
 another SliceSet's base ---------^ (same Rc: ptr_eq shortcut)
```

`absorb` takes the other set's run by reference when this set has none or
the same one, and copies slices otherwise. `retain` and `retain_outliving`
ask the run as a whole where `shared_kept` can answer, and `materialize` it
into `own` where only per-slice tests can. `coalesced` drops the subranges
of an object the set has every byte of; the run is materialized only if its
own wholes and parts disagree or the set's own wholes cover a part of it.
`mapped` rewrites `own` and keeps the run, so the map must not change what
the run holds. Equality compares by `Rc::ptr_eq` and `own` when the runs are
the same.

### Provides
`SliceSet`, `Shared` and `whole`. Consumers: `crate::alias` (call
summaries and `callbacks_over`, via `crate::manager`'s `Callbacks`) and
the `interprocedural` pass in llrm-transforms.

## ssa

Source: [`crates/opt/llrm-analysis/src/ssa.rs`](https://github.com/ali-mosavian/llrm/blob/main/crates/opt/llrm-analysis/src/ssa.rs)

SSA helpers: use lists, dead-phi pruning, value substitution and an SSA
updater.

### How it works
`use_index` maps each value to the non-phi instructions that read it, in
layout order, each at most once; `values` lists the values a function
mentions.

`pruned_phis(function, roots)` removes phis nothing needs, including cycles
that only other dead phis read. A value is needed when a root or a non-phi
instruction reads it, or a needed phi reads it; the rest of the phis are
erased (their operands first, since only dead phis read dead phis). It
reports whether any went.

`provider(value, swap)` follows a substitution map from a value to an
operand (a value may be replaced by a constant) until it reaches one the map
does not move; a cycle is `SubstitutionError::CyclicValueSubstitution`.
`substituted` reads each operand of an instruction through it and leaves the
definition alone.

`SsaUpdater` is LLVM's SSAUpdater for one value defined in several blocks.
`add_available_value(block, v)` says `v` is the definition at the end of
`block`. The value at the end of any other block is what reaches it from its
predecessors. One predecessor passes the question up; no predecessor reads
`poison`; several place a phi at the head of the block, one input per edge
(a `switch` may reach a block by several), asked of the predecessors. A phi
whose inputs are all one value, ignoring itself, is replaced by that value.
`rewrite_use` makes a use read the value where it reads: a phi's input at
the end of the block it comes from, any other at the middle of its block.
`inserted_phis` lists the phis placed that stand.

```text
      A: v1 = ...          available: A -> v1, B -> v2
     / \
    B   C                  value_in_middle_of_block(D):
    v2  |                    preds B, C -> phi placed in D
     \ /                       D: %p = phi [v2, B], [v1', C]
      D: use v             C has one pred A -> passes v1 up
```

### Provides
The helpers above. Consumers in llrm-transforms: `dead`, `promote`
(`pruned_phis`); `gvn`, `lcssamerges`, `transform`, `loadjoins`
(`substituted`, `provider`); `rotate`, `jumpthread`, `floatloop`
(`SsaUpdater`).

### Needs
`crate::occurrence` for the operation and phi walks.
