# llrm's m32 against its m16

For maintainers checking the requirement that m32 code is at least as good as m16: the same program, compiled by llrm for both targets at one `-O` level, run on a 486. No result is kept here; the tool prints the table, and a number in a document stops being true when the compiler moves.

## What is measured

Per program and level, the kernel's executed instructions, memory operands and 486 clocks at each target, and the ratio m32/m16. A ratio above 1.00 is a row m32 loses; the table flags it with `<`. A language's geomean and worst row follow each level's rows.

| Language | m16 | m32 | Counted |
|---|---|---|---|
| C | `tools/bench` `c` (real-mode unicorn, inlining on, the kernel called through a volatile pointer as vsgcc does) | `vsgcc/harness.py` `llrm*` (unicorn, the kernel a call through `wrap.py`) | instructions, memory operands, clocks |
| QuickBASIC (`llrm-qb`) | `bq16` | `bq32` | instructions only: `tools/bench` counts the flat build in DOSBox |

The two C counters share one clock table (`cost()` in `vsgcc/harness.py`), so clocks compare. A row is a `bench/` program both sides build; the `x_` kernels have no m16 build here, and `jpeg_*` and `stft_*` have no m32 C build (file input). Nib has no m32 build, so it has no row.

The requirement is read from clocks where they are measured and from instructions where not (BASIC). A count of none is read as one, so a ratio is always defined; a memory-operand ratio over a count of a few is noise, read it by the counts.

## Run it

    uv run --project tools python crates/target/llrm-x86-m32/vsgcc/against_m16.py --run     # measure both targets, print the tables
    uv run --project tools python crates/target/llrm-x86-m32/vsgcc/against_m16.py           # print them from the files of the last run

`--run` takes about ten minutes: it runs `tools/bench/bench.py --opt O1 O2 O3 Os --json` and builds and runs every program's four llrm variants (`VSGCC_ONLY=llrm` leaves `build.sh` with no gcc or clang to build). It needs gcc and GNU `ld` for the stub only. The files go to `$VSGCC_WORK` (`bench-m16.json`, `results-m32.jsonl`); `--bench` and `--vsgcc` name others.

## Limits

- The two counters are not one machine: m16 is a 16-bit real-mode stream, m32 a flat 32-bit one, and the clock table prices both as a 486 would. It says which build executes more, not what a given chip does.
- Start-up, the runtime and `report` are outside the counted kernel at both targets.
- BASIC at m32 has no clocks, so a BASIC row can pass on instructions and still lose on clocks.
